# G5 — state compatibility (TS v46 daemon vs Rust daemon)

**Result: PASS.** 205 of 205 checks passed, in three consecutive full runs on 2026-10-19/20 (branch `x4/gates-state`,
base `rust-port` 28ce4a0, `target/release/deckhand` built from that tree, `dist/` from `npm run build` of the same
tree). No Rust divergence was found.

```
npm run build && cargo build --release -p deckhand
node scripts/gates/state-compat.mjs [--keep] [--report <file.json>]   # exit 0 = every check passed
```

The script is `scripts/gates/state-compat.mjs` (plain node, no dependencies). Each run builds its own sandboxes under
`$TMPDIR` and removes them unless `--keep` is passed.

## Setup

- **Two identical sandboxes.** Each run builds two sandboxes, `ts` and `rs`. Both use the same deterministic steps
  from `fixtures/state/sandbox.json`: git repos `repos/app` and `repos/lib`, the worktrees `feature-a`,
  `feature-merged` (merged), `legacy` and `attached`, and a non-git `plain/`. The script checks every SHA against
  `sandbox.json` `expect`, so the repos are byte-identical. It then copies `fixtures/state/home-v45` into each one.
  Placeholder paths and path-hash note names are rewritten and the modes manifest is applied, all as
  `parity/gen/state.gen.ts` does.
  - **Why not one shared set of repos?** Phase (c) creates and deletes git worktrees and branches. Two daemons
    working on one repo at the same time would collide, for example on `branch already exists`.
- **Environment.** Each daemon has its own `HOME`, XDG dirs, `TMPDIR`, `CLAUDE_CONFIG_DIR` and `CODEX_HOME` inside
  its sandbox, and uses the env from `fixtures/state/README.md`. It runs with cwd `repos/app` and umask `022`.
- **Fake agents.** `claude`, `codex` and `pi` on `PATH` are the `fakeAgent` from `tests/helpers.ts`, with these
  changes:
  - `--version` prints the `sandbox.json` version strings.
  - The shebang is an absolute path to node.
  - Their own `trace-`/`ready-`/`input-` files go to `$FAKE_AGENT_STATE`, outside `DECKHAND_HOME`, so they never
    enter the compared tree.
  - Their `$TEST_CLI hook` is the implementation under test: a `node dist/cli.js` shim for TS, the Rust binary for
    Rust.
- **Daemons.** TS runs `node dist/cli.js --daemon`; Rust runs `target/release/deckhand --daemon`. Every read and
  write goes over each daemon's `daemon.sock`, one connection per request.

  they spawn shells and none of them writes state beyond `devRunning`.

## Normalisations

Normalisation applies only to values that are volatile by construction. Each side has its own normaliser, which is
kept for the whole run, so a given fresh ID gets the same token in every snapshot:

| token | replaces | why it is volatile |
|---|---|---|
| `/tmp/deckhand-fixture` (+ fixture note hashes) | the sandbox root, its unresolved `$TMPDIR` spelling, and path-hash note names | each sandbox has its own root; `repoNoteId` hashes the path |
| `<now>` | ISO timestamps within the run (±1 s) | `createdAt`/`updatedAt`/`agentStartedAt`/`attention.at`/`mergedAt`/`checkedAt`/… |
| `<now-ms>` | integer epoch-ms within the run | (none observed) |
| `NOW_` | the `YYYY-MM-DDTHH-MM-SS_` prefix of trash file names written during the run | `trashFileName` |
| `done=<today>` / `added=<today>` | task dates equal to the run's UTC day | `applyTaskOp` `today` |
| `<uuid-N>` | v4 UUIDs not present in `home-v45`, numbered by first appearance (state.json first) | session IDs, launch IDs, worktree record IDs, claude `--session-id` |
| `<uuid-N:8>` | the first 8 hex digits of such a UUID | agent session names `dh-<title>-<id[0..8]>` (src/daemon.ts:267) |
| `t=<task-N>` | task IDs not in `home-v45` | `newTaskId` (random 4 bytes) |
| `<handoff-N>` | the random 8 hex digits in `handoffs/<id>-<rand>.md` | `randomUUID().slice(0, 8)` (src/sessionFeatures.ts:97) |
| recomputed `revision` | a note revision whose text changed under the tokens above | `noteRevision` hashes the text |
| `<pid>` | `"pid": N` in state.json and responses, the contents of `daemon.pid` and `workers/*.pid` | OS process IDs |
| `<user>` | `settings-info` `user` | the OS account |
| `<deckhand-cli>` | the implementation's own executable in the claude `--settings` hook command: TS `'<node>' '<dist/cli.js>' 'hook'`, Rust `'<target/release/deckhand>' 'hook'` | each implementation runs itself |
| `<volatile>` | `daemon.log` contents (its mode is still compared) | wall-clock lines, pids, timing-dependent order |
| sorted keys | the `worktree-candidate-sizes` response map only | TS fills it in the order its concurrent size reads finish (src/settingsInfo.ts:275); see below |

The comparator is byte-sensitive. Before the `<pid>`, `<deckhand-cli>`, `<uuid-N:8>` and `<handoff-N>` rules
existed, the first run flagged exactly those values (61 failures), and nothing else.

## Notes

- **Not a Rust bug: `worktree-candidate-sizes` key order.** In TS the key order depends on timing. The first run
  saw `{… "missing": null, "src": 8}` from TS, against request order `{… "src": 8, "missing": null}` from Rust,
  because TS's lstat of a missing path finished before its directory walk of `src`. Rust's request order is one of
  the orders TS can produce. Clients look the map up by key.
- **Upgrade restart, in passing.** The idle start reproduces the v45 crash-recovery migrations recorded in
  `fixtures/state/MIGRATIONS.md` identically on both sides, which (b) covers.
