## Snapshot

Deckhand is a native Rust program: one binary, `deckhand`, backed by a long-lived local daemon (the same binary re-launched with `--daemon`). It was ported from the original TypeScript/Ink app. The port is complete: Rust behaviour can evolve, but a state directory written by the TypeScript version must keep loading (`fixtures/state`). It is inspired by `claude-squad`, but owns its own state, IPC protocol, worker model and session lifecycle. Supported agents: `claude`, `pi`, `codex`.

- Cargo workspace (`crates/*`), edition 2024, `rust-version = "1.88"`, version in `[workspace.package]`; the binary crate is `crates/deckhand` (package `deckhand`, `publish = false`). `[profile.release]`: thin LTO, one codegen unit, stripped.
- macOS and Linux only (Unix PTYs, `setsid`, Unix sockets).
- Install: the shell installer (`deckhand-installer.sh` from the latest release, into `$XDG_BIN_HOME`, else `$XDG_DATA_HOME/../bin`, else `~/.local/bin`), a release archive, `cargo install --git https://github.com/tejgor/deckhand deckhand` or `cargo install --path crates/deckhand`. Nothing is published to npm or crates.io.
- Release: [dist](https://github.com/axodotdev/cargo-dist) 0.32 (`dist-workspace.toml`; `[package.metadata.dist]` in `crates/deckhand`). Tag `vX.Y.Z` equal to the workspace version; `.github/workflows/release.yml` is generated by `dist generate` (never edit it by hand; `dist plan` checks the config) and builds `deckhand-<target>.tar.xz` (binary, README, LICENSE) for `aarch64`/`x86_64` `apple-darwin` and `unknown-linux-gnu`, each with a `.sha256`, plus `sha256.sum`, `source.tar.gz`, `deckhand-installer.sh` and the Homebrew formula `deckhand.rb`, then pushes the formula to `tejgor/homebrew-tap` (needs the `HOMEBREW_TAP_TOKEN` secret; the release is not announced if this fails) and creates the GitHub release. Its post-announce job `.github/workflows/release-notes.yml` (`post-announce-jobs = ["./release-notes"]`, a `workflow_call` workflow taking dist's `plan`) appends the **Daemon restart** line from `scripts/release-restart-note.sh <tag>`: *required* when `PROTOCOL_VERSION` differs from the previous stable `v*` tag's, *not required* otherwise, and the npm-upgrade pointer when no earlier tag has `crates/protocol` (tested in `crates/e2e/tests/release_notes.rs`).
- Debug builds refuse `~/.deckhand` unless `DECKHAND_ALLOW_PROD_HOME=1` (`crates/deckhand/src/guard.rs`); use the dev launcher.

### Processes, workers and the fd-3 channel

One executable, several roles chosen by argv (`crates/deckhand/src/cli.rs` `parse_args`, in this order): `status`/`stop` (dev channel only), `hook`, `hooks [codex]`, `--session-worker`, `--workspace-worker`, `--daemon`, `setup`, `doctor`, `restart`, `--version`, otherwise the UI.

- The UI is a disposable frontend; quitting it never stops sessions. The daemon is the source of truth for persisted session metadata and routes live control. Workers own the PTYs: a session worker per running session (its agent), a workspace worker per worktree whose Terminal/Git/Dev/action panes are in use.
- The daemon starts each worker by re-executing the binary with `--session-worker` or `--workspace-worker` and handing it one end of a `socketpair` as **fd 3**. The channel carries NDJSON (`deckhand_protocol::ndjson`). The worker's first message is `hello` with `{version: PROTOCOL_VERSION}`; a worker speaking another version is closed and its requests fail (the launch is reported failed). Requests are `{...payload, requestId}` (ID last), answered by a `response` with the same ID; every other message (`running`, `exit`, previews, output, ...) is an event delivered in order, followed by one exit event when the channel closes. Worker stdout/stderr go to `workers/<id>.log`, PIDs to `workers/<id>.pid`.
- A worker crash exits only that session (or stops only that workspace's panes); its last preview stays frozen. A daemon crash or restart does **not** preserve live PTYs: at the next start the daemon marks persisted non-exited sessions exited (`markAllNonExitedSessionsExited`, which also writes back migrated state and clears `devRunning`).
- Daemon start order: load state (lifting legacy per-session worktree markers into worktree records and done markers, and legacy `notes` into `notes/` files), read every note file, start the notes watchers, mark previously running sessions exited.
- Client (`crates/client/src/client.rs`): pings; auto-starts the daemon (re-exec with `--daemon`, output appended to `daemon.log`) only when the socket is missing/stale and no live daemon PID exists; removes a stale socket only then; retries when the PID is alive but ping fails, then errors instead of replacing it; refuses to replace a live daemon with another protocol version (*a daemon restart is required: run deckhand restart (or stop the old daemon yourself: kill <pid>, …)*): replacing it would interrupt every running session, so only an explicit `deckhand restart` does that.
- Daemon updates (`crates/core/src/daemon_build.rs`, `crates/deckhand/src/restart.rs`): a daemon runs the binary it started from, so after an update of the same protocol the client keeps using the old daemon (and its old worker code). `ping` also answers `build` (`deckhand_protocol::BUILD_VERSION`, the workspace version) and `pid`, added without a protocol bump: the client reads them as optional (`check_ping_version` reads fields one by one), so an older daemon of the same protocol still works. When the build differs, the UI (`daemon_build_notice` in `crates/ui/src/app/effects.rs`, after each subscribe) shows `Daemon 3.0.0 is still running (this is 3.0.1) · restart when convenient: deckhand restart` once per daemon: the status slot's 5 s auto-hide, plus the next key (`App::show_notice`, `Messages.notice`), keyed by daemon pid + daemon build + client build in its own file `daemon-notice` (`deckhand_sys::daemon_notice`; deliberately not a key in ui-state.json/state.json/config.json, which other versions read). A daemon without `build` predates it and counts as older; one without `pid` is keyed by `daemon.pid`. `deckhand doctor` prints the daemon line (informational; exit status unchanged). `deckhand restart [--yes]` (`deckhand_client::client::{daemon_state, count_live_sessions, stop_daemon}`): no daemon → starts one; otherwise counts non-exited sessions with `list` read as plain JSON (so an other-protocol daemon answers too), asks on a TTY when any (or an unknown number) would be interrupted, refuses without a TTY and without `--yes` (exit 1), sends `shutdown` (only the dev channel accepts it), else SIGTERM to the reported pid (else `daemon.pid`), waits 10 s, then SIGKILL (and removes the stale pid file and socket). "Gone" is the process gone, or `daemon.pid` no longer naming it and the socket no longer answering: an exited daemon its parent has not reaped still answers `kill(pid, 0)`. Then `ensure_daemon_running` starts this executable's daemon (with the restart command's environment, `PATH` included) and it prints `Daemon restarted (3.0.0 → 3.0.1).`

### Subsystem notes

#### Workspaces and workspace workers (`crates/worker/src/workspace.rs`)

A **workspace** is the git worktree a session runs in. It is derived, never persisted: `workspaceKey(session)` is the resolved worktree path for managed/attached sessions (including a session attached to the main checkout), otherwise the launch checkout root (`launchWorktreeRoot`, falling back to `cwd` for old records). It is undefined, so the session has no workspace and no Terminal/Git/Dev, when the worktree was deleted (`worktree.deletedAt`, projected from the worktree record onto every session of it, so no session of a deleted worktree shares a workspace with a new worktree later created at the same path) or while a requested new/existing worktree is not prepared yet (it would otherwise resolve to the launch checkout). The daemon also treats sessions in `preparingSessions` as having none until `launchWorktreeRoot` is resolved by Git; it reports that as a pane record without `workspace`, which `workspacePaneUnavailable` (UI) turns into the *not ready yet* message. Keys are lexical; every input path comes from Git (`rev-parse --show-toplevel`, `worktree list`), so they agree.

Terminal, Git and Dev are owned by the workspace: one workspace worker per workspace whose panes are in use, spawned by the daemon on the first `watch-terminal`/`watch-git`/`attach-terminal`/`attach-git` or `start-dev`/`run-action` (`startsOnView` is true only for Terminal and Git, so `watch-dev`/`watch-action` and `attach-dev`/`attach-action` never open one). PID/log at `workers/workspace-<sha256(key)[:16]>.pid|.log` (`workspaceWorkerId`). `openWorkspace` refuses a worktree in cleanup (`assertWorkspaceAvailable`) or whose directory is gone (*Worktree directory is missing*). Why a process rather than daemon-owned PTYs: PTY I/O and terminal parsing (a chatty dev server, a busy shell) stay out of the daemon's event loop, a PTY crash cannot take the daemon down, and the daemon owns no PTYs at all. The cost is one mostly idle process per workspace in use.

Semantics (daemon `requireWorkspace`/`openWorkspace`/`watchWorkspacePane`/`attachWorkspacePane`/`requestPane`/`retireIfIdle`/`retireWorkspace`/`publishWorkspacePane`/`syncDevRunning`):

- Every Terminal/Git/Dev/action request (`watch-*`, `attach-*`, `*-input`, `*-resize`, `*-detach`, `start-dev`, `stop-dev`, `run-action`, `stop-action`) still names a session; the daemon resolves its workspace and acts on the one shared pane. Sessions in one worktree share one shell, one lazygit and one Dev; another worktree has its own. Starting Dev from any session starts (or reuses, same command) the shared process; stopping from any stops it. The Dev command is resolved from that session's effective settings (`resolveDevCommand`).
- The panes run independently of agents: view/attach (and Dev start/stop, actions) work for starting (once prepared), running and exited sessions alike.
- Lifetime: the worker is retired (all panes stopped, awaited) when kill-with-delete removes the worktree (after the cleanup checks pass, before `git worktree remove`), when the workspace's last session is removed (nothing could show or stop the panes otherwise; a shell never exits on its own), and when the daemon stops (`cleanup` retires every workspace; on a daemon crash the worker's IPC disconnect stops its panes). It is also retired once it is **idle** and no pane request is in flight (`busy`): after `stop-dev`/`stop-action` (`stopWorkspacePane`; no Terminal/Git/Dev/action runtime left) and after a failed pane request (`requestPane` → `retireIfIdle`, e.g. lazygit is not installed), so a failed view never leaves an empty worker behind. Its own panes never make it idle: a shell or lazygit that exited, like a Dev that exits on its own, keeps its runtime so the output stays visible.
- Records: the worker's records carry no session; the daemon stamps each watching client's session ID plus `workspace` (`TerminalRecord`/`GitRecord`/`DevRecord`/`ActionRecord`) and sends `<pane>-updated` to every client watching that pane on any session of the workspace (`publishWorkspacePane`). The last record per pane is kept in `WorkspaceRuntime.records`: on an unexpected worker exit viewers get it back marked not live; on retirement they get an empty not-live record (only panes that existed). One attach per workspace pane (*terminal/git/dev command/action is already attached elsewhere*); output goes to the attaching socket as `<pane>-output` under its session ID; retiring the worker sends `<pane>-detached` to it. Each PTY is sized by the last watch/attach/resize of that pane (last viewer wins).
- `devRunning` stays on `SessionRecord` (so every response/broadcast carries it) but mirrors the workspace: `syncDevRunning` sets it on every session of the workspace, exited ones included, whenever the worker reports a Dev record, and `saveSession`/`saveWorktreeRecord` re-derive it for sessions that join or leave a workspace (create, worktree deleted).

**Actions** (`run-action`, `startWorkspaceAction`): an action runs in the workspace's own `action` PTY, never in the shell or Dev, and the UI shows it on the Terminal tab. Rejected alternatives: running it in the Dev PTY (what protocol < v40 did: refused while the dev server ran, and replaced its output), typing the command into the shared shell (no exit code, no stop, collides with whatever is typed or running there) and a tab of its own (the user did not want another pane). The daemon resolves the command from effective settings and refuses an untrusted repository action. `ActionRecord` is `DevRecord` plus `name`. Actions do not touch `devRunning`/`▶`.

**Dev processes** (`devCommand` as a name → command map in `deckhand.json` or the global defaults): Dev can run several named commands side by side, the replacement for a tmux wrapper script that starts a backend and a frontend, asked for so both logs stay visible while debugging.

- *Config*: `devCommand` is a string or (`DevCommand::Processes`) a name → command map validated like `actions` (names, at most `MAX_DEV_PROCESSES` (8), no empty command). One key on purpose (the user did not want two settings for one thing): a layer's `devCommand` replaces the other's whole, as any scalar does. `ProjectConfig::dev_command_text`/`dev_processes` read it; `resolve_dev_plan` returns `DevPlan::Command` or `DevPlan::Processes`. Untrusted repository processes never run. `explain_settings` sums a map up in the `devCommand` row (`dev_command_summary`) and adds a `devCommand` row per process (with `entry`) only while a map applies or is pending, so a single command's rows are unchanged.
- *One worktree at a time*: every worktree runs the same Dev config, so the same ports. `handle_start_dev` calls `stop_dev_elsewhere` first: it stops Dev in every other workspace of the repository's sessions (`repository_sessions`). Asked for in place of a wrapper script that killed whatever held the ports; deliberately not a setting. The UI names the stopped worktrees in its status (`dev_elsewhere`).
- *Worker*: `PaneTarget::Dev(u8)`: a single command is `Dev(0)`, named processes `Dev(0..n)` in configured order, each its own PTY and pump. `PaneHost.dev_processes` holds the started list (`None` for a single command). There is still one Dev pane on the wire: `dev_record()` builds one record with `processes` (`live` = any live, so `devRunning`/`▶`/`D` need no change), and every process's broadcast posts that whole record. `snapshot` sizes every process alike (the UI sends the cell size from `dev_cell_size`); `attach` with `process` sizes only that one and marks it the attached Dev target, so `input`/`resize`/`detach` (which carry no process) route to it and only its output is forwarded. `start-dev` with `processes` keeps running processes whose name and command are unchanged and refuses any other running one (*Stop the current Dev command before starting another*); `process` starts one alone, `restart` stops it first and awaits its exit (port release). `stop-dev` with `process` stops one and keeps the list; without, it stops all and forgets the list.
- *Daemon*: one Dev attach per workspace still (attaching another process elsewhere is *already attached elsewhere*); `stopped_record` keeps the processes' last output, marked not live, after a worker crash.
- *UI*: `panes::dev` splits the tab (`dev_split`: side by side while each column is ≥ `MIN_DEV_COLUMN` (40), else stacked); `v` selects (`PaneRecords.dev_process`, by name, carried across the attach round trip by `ui_loop` as `initial_dev_process`); `enter` attaches the selected process (`UiExitResult::Attach.process` → `AttachSessionOptions.dev_process` → `Attach.process`). The run list adds a row per process after Dev (`App::run_list_processes`, from the effective settings; opening the list watches Dev so their state is fresh). Settings keeps one Dev command row, and `enter` on it always opens the list of what Dev runs (`SettingsFlow::list_id`, `SettingsPaneProps.list`, `handle_dev_list`), even with one command or none: the user preferred one consistent screen to a text input that turns into a list. Its edits are `SettingsEdit::Process`, two steps every time (`ProcessStep`): the command, then the name, pre-filled by `derive_process_name` when adding and with the process's own name when editing, so Enter twice accepts both (the user wanted the suggestion editable in place rather than a separate rename). `dev_command_change` (`DevEdit::Add`/`Update`/`Remove`) writes the whole `devCommand` as a map; a hand-written plain command is listed under its derived name and stays plain only while edits keep that name.

**Several shells** (protocol v53; the user wanted a second terminal in a worktree without tying shells to sessions):

- *Worker*: `PaneTarget::Terminal(u8)`, the shell's id: the first is `Terminal(0)`, extra ones (`new-terminal`) get the next id from `PaneHost.next_shell` and keep it while they run (ids are not reused while the worker lives, so a request never lands on a different shell). At most `MAX_SHELLS` (4). `terminal_record()` is the one Terminal record: the first shell's own, plus `shells` (every shell: `ShellRecord {id, content, live, screen?}`) once there is more than one, so with one shell the record is unchanged; every shell's broadcast posts it. `snapshot` starts the first shell (as before) and sizes every shell alike; `attach` with `shell` marks that one the attached Terminal target (`input`/`resize`/`detach` without `shell` route to it); `input` with `shell` types into that one without an attach. An extra shell that exits is forgotten at once (`on_pane_exit`), and `close-terminal` stops one (never the first: it restarts, *The first shell restarts rather than closes*). `restart-terminal` takes `shell`.
- *Typing into a shell* (terminal focus, below): `preview-mode {target: terminal, styled, shell}` adds that shell's styled screen (top-level `screen` for the first, `shells[i].screen` otherwise) and puts its broadcasts on the 8 ms pace. The daemon keeps `ClientSubscription.terminal_interactive_shell` and `WorkspaceRuntime.styled_shells`, and `sync_terminal_styled(key)` sends a `preview-mode` per change (watch, session switch, disconnect); `without_screens` strips them for every other watcher and from the `restart`/`new`/`close-terminal` answers.
- *Daemon*: one Terminal attach per workspace still, on one shell (`WorkspaceRuntime.attached_shell`); restarting or closing that shell, or it exiting (gone from the worker's next record, `detach_from_gone_shell`), detaches its client.
- *UI*: `TerminalView::Shell(id) | Action`; `panes::terminal::shells`/`shown_shell`/`shell_label` (labels are by position: `shell 1`, `shell 2`; a single shell is just `shell`); the header lists them, the shown one bold. `v` cycles the shells then the action. The run list (`action_picker`) has a row per shell (Enter shows it; x twice closes an extra one or restarts the first) and `+ New shell` while below the limit; it lists only the first shell when the Terminal record shown is another session's. The attach hand-off carries `shell` and `shell_label` (`UiExitResult::Attach`, `AttachSessionOptions.shell`) so the status line says which.

Adding another workspace pane: a PTY pane is a `PaneTarget` in `WORKSPACE_PANES` (worker) plus `WorkspacePane`/`WorkspaceEvent`/`paneUpdatedMessage` and the request cases in the daemon. A non-PTY workspace view does not need the worker: compute it in the daemon from the workspace key (like `workspace-summary`, `crates/sys/src/workspace_git.rs`) or, if it must push updates, keep a per-workspace watcher and fan out like `publishWorkspacePane`, as the Changes view (below) does.

#### Worktree records: shared merge/deleted markers (`crates/core/src/worktree_records.rs`)

Merge and deletion markers describe a worktree, not a session, so every session in a linked worktree shares them. State: one `WorktreeRecord` per worktree **incarnation** (`{id, path, createdAt}` plus the markers `mergedAt`/`mergeMode`/`mergeTargetBranch`/`mergeSourceRef`/`mergeSourceSha`/`mergeMarkedManually`/`mergeDetected`/`deletedAt`, and two unprojected fields `baseSha`/`mergeDismissedTip`), persisted in `state.json` `worktrees`; sessions store only its ID as `worktree.id`.

- `mergeSourceSha`: the source commit Deckhand merged (`mergeSourceRef` is a branch name that moves on), or the head of a PR found merged; cleanup treats it and its ancestors as integrated (see *Deletion safety*). Never set by `M` (unverified) nor for a kept conflict whose pending record was lost.
- `mergeDetected`: `'ancestor'` or `'pr'` when the marker was set by merge detection rather than by `m`/`M`.
- `baseSha`: where the branch started (its reflog's `branch: Created from …` entry, else HEAD when the record was created; filled in lazily from the reflog for older records). Merge detection needs a commit beyond it.
- `mergeDismissedTip`: the branch tip when `M` cleared the marker; detection leaves the record alone while the tip is unchanged. Dropped whenever markers are set.
- **Scope**: sessions running in a linked (non-main) worktree: managed or attached, and sessions without their own worktree (mode `none`, e.g. sub-sessions from `N`) launched in one (`isLinkedWorktreeRoot`, from `git worktree list`). The main checkout (mode `none` there, or attached to the main worktree) has no record and no merge marker: `M` refuses there (*… Use Space to mark it done*; it can still clear a leftover marker), and such sessions use the per-session done marker (`doneAt`, Space, `set-session-done`; independent of merge markers).
- **Incarnations** (`joinWorktree`, called in `finishCreateSession` with no await between the lookup and setting the session, so the record cannot be dropped as unreferenced in between): attaching an existing worktree, or a mode-`none` session launched in one, joins the live record at that path (at most one per path; created if none). A worktree Deckhand just created (`origin: 'created'`) always starts a new record; a live record still at that path means the old worktree was removed outside Deckhand, so it is marked deleted (`superseded`). A deleted record is never joined, so old sessions never share a later worktree at the same path.
- **Projection**: the daemon's `sessions` map (`SessionMap`) projects the record's markers into `session.worktree` on every `set`, so every reader (`workspaceKey`, restart/merge/create-pr guards, `cleanupBlockers`, handoff export, the UI's `✓`, hints and `M` status) keeps reading `session.worktree.mergedAt`/`deletedAt`. `persist()` writes `storedSession` (projection stripped) plus the records: the record is the only persisted copy. `saveSession`/`patchSession` return the projected session.
- **Writes**: `saveWorktreeRecord` replaces a record, re-sets (re-projects, re-derives `devRunning`) and bumps `updatedAt` of every session referencing it, persists once, broadcasts `session-updated` for each, re-syncs Changes watches and syncs linked tasks. Used by merge success and a kept conflicted merge (`saveMergeMarkers`), `M` (`markSessionMerged` → `saveMergeMarkers`: replaces or clears the merge markers wherever they live; clearing stores `mergeDismissedTip`), merge detection (`markDetectedMerge`), kill-with-delete (`markDeleted`, after `stopChangesWatch` → `retireWorkspace` → `removeWorktree`) and superseding. `updateWorktreeRecord(…, false)` patches an unprojected field (`baseSha`) without touching sessions.
- **Lifetime**: `removeSession` drops the record once no session references it; loading drops unreferenced records too.
- **Migration** (`migrateWorktreeRecords`, run by `loadState`): sessions without `worktree.id` are grouped by worktree root (their own linked worktree; for mode `none`, the launch root when some session owns a linked worktree there). Each recorded `deletedAt` ends one incarnation: the session that deleted it belongs to it, any other session to the first deletion at or after its last launch (`agentStartedAt`, else `createdAt`), and the rest to the live incarnation (joining an existing live record at that path). Each incarnation takes the most recent merge marker of its sessions (a mode-`none` sub-session's top-level `M` marker included, then removed from the session). It also repairs stored state: stray markers on sessions with an ID are dropped, a missing referenced record is rebuilt from the session. Idempotent and unit-tested.
- **Done migration** (`migrateDoneMarkers`, right after): before Space/`D`, `M` doubled as "done" in the main checkout. Every session without a worktree record that still has its own merge marker (top-level `mergedAt`/`mergeTargetBranch`/`mergeSourceRef`/`mergeMarkedManually`, or the merge markers under `worktree` of a main-worktree attach) gets `doneAt = mergedAt` (an existing `doneAt` wins) and loses those fields. Idempotent and unit-tested beside the record migration.

#### Worktree manager (`crates/core/src/worktrees_model.rs`, `crates/ui/src/flows/worktrees.rs`; daemon `worktreeOverview`/`inspectWorktree`/`deleteWorktree` in `crates/daemon/src/worktrees.rs`)

Asked for because nothing showed all worktrees and which were merged, and deleting one meant `x` on a running session of it (exited sessions' worktrees could not be deleted from Deckhand at all; worktrees made with `git worktree add` were invisible). The user wanted deletion to stop the worktree's sessions itself rather than having to stop each first.

- **Overview** (`worktree-overview`, `cwd`): `findRepoRoot(cwd)`, then `detectMerges` for the repository's live unmarked records (awaited, so the list says what is merged now), `listWorktrees` (with `locked`/`prunable` from the porcelain output), and entries for live records of the repository's sessions whose path Git no longer lists (`missing: 'unlisted'`). The repository's sessions are every session whose `repoRoot` has the same tasks key (`repositorySessions`, like `inClientScope`); an entry's sessions (`sessionsInWorktree`) are its live record's, those whose `workspaceKey` is the path, and (not for the main checkout) any not exited whose cwd is inside it; a deleted incarnation's sessions never count for a later worktree at the same path. `inUse`: `this` when the asking checkout is that worktree, `other` when another subscribed client's `repoRoot` is (realpaths). Linked, present worktrees get `inspectWorkspaceCleanup(…, {deleteBranch: true, integrated: mergeSourceSha})` and `worktreeActivity` (last commit, `rev-list --count HEAD --not <default refs>`), at most `WORKTREE_OVERVIEW_MAX` (60), four at a time (`forEachLimited`); the rest are counted in `unchecked`. Nothing is polled: the UI reloads on open, after a deletion and on `R`; which sessions run comes from the live session list.
- **Groups** (`worktreeGroup`, pure, unit-tested): merged = a record merge marker, or no commits beyond the default branch **and** a clean inspection (a fresh branch with uncommitted work is in progress, not merged); merged + `inspection.safe` → `ready`, else `leftovers`; not merged → `idle` when nothing runs and the latest of last commit / record creation / session `updatedAt` is over `IDLE_DAYS` (14) old, else `progress`; `missing`; `main`. A squash marked with `M` (no `mergeSourceSha`) has commits only on its branch, so it is `leftovers` (deleting the branch needs DELETE), by design of the deletion rules.
- **Checks** (`inspect-worktree`, `worktreeBlockers`): structural blockers mirror `cleanupBlockers` for a worktree rather than a session: main checkout, the asking checkout, another client's checkout, locked, already being deleted (`cleanupWorktrees`), branch changed since listed (`branch` in the request), branch deletion of a detached HEAD or of `main`/`master`/the default branch, a session still `starting`. Running sessions are not a blocker; the check returns them (`running`). Missing worktrees have none (nothing on disk is touched).
- **Deletion** (`delete-worktree`): check (data reasons need `allowDataLoss`); refused while sessions run unless `stopSessions`; adds the path to `cleanupWorktrees` (new panes refused, merge detection skips it); stops each running session (`stopForDeletion`: `killSession` without delete, then waits up to 10 s for `exited`); checks again if it stopped any (they may have written files); `stopChangesWatch` + `retireWorkspace`; `removeWorktree`; `deleteLocalBranch` when asked. A `prunable` one runs `git worktree prune` (every stale entry of the repository; the branch stays); an `unlisted` one only has its record marked. Then `saveWorktreeRecord({deletedAt})` (unmerged work's task goes back to the backlog as with kill-with-delete) and every exited session of it is archived (`stopped`/`archived` counts in the result). The kill-with-delete path in `handleWorkerSessionExit` does not archive.
- **UI** (`WorktreesFlow`, mode `worktrees`, `W`): rows like the Tasks board (headings, `› glyph name … tags`, details below: state, path, sessions with their status glyphs, what deletion would lose). The ready heading is selectable: `x` there deletes `bulkTargets` (ready, not `inUse`, not locked) sequentially, branches too unless protected, stopping sessions, after one confirmation listing them; failures are collected into one error. `x` on a row asks: keep-branch / with-branch (with-branch first for merged work), labels prefixed *Stop N sessions,* when some run; both inspections are requested when it opens; a data reason opens the typed-DELETE override. `enter`/`o` selects its lead session (`leadSession`, via the same `goToSession` the Tasks board uses), `M` toggles the record's marker through one of its sessions, `E` opens the path, `R` reloads.

#### Notes (`crates/core/src/notes.rs`, `crates/sys/src/notes_store.rs`, `crates/ui/src/flows/notes.rs`, `crates/ui/src/panes/notes.rs`)

One note per place you work, plain Markdown files under `notes/` in the state directory, the single source of truth. A session in a worktree has one note, the worktree's (`showsOwnNote` false); a main-checkout session has its own and the repository's. Decided with the user after their data showed 8 session notes and 0 worktree notes, and a removed parent session took a worktree's to-dos with it while its ~14 sub-sessions lived on: a worktree's notes belong to the worktree, not to its most short-lived session; main-checkout sessions are separate jobs, so they keep their own.

- **Session note**: `notes/sessions/<session id>.md`, shown for main-checkout sessions (and for a worktree session that still has text in one, so nothing is ever hidden). `save-note` refuses a worktree session's own note when empty. `mergeWorktreeSessionNotes` (daemon start, after `load`, before sessions are projected) merges worktree sessions' own notes into the worktree note (`mergeIntoWorktreeNote`: a lone note into an empty worktree note as it is, else each under `## <title>`, sidebar order), then trashes the originals; a merge that would exceed `MAX_NOTES_CHARS` is skipped and logged.
- **Shared note** (`sharedNoteIdentity`): a session with a worktree record (`worktree.id`, mode-`none` sub-sessions in it included) shares `notes/worktrees/<record id>.md` with every session of that incarnation; a new worktree at the same path is a new record, so it starts empty. A session without a record but with a workspace (the main checkout) shares the repository note `notes/repos/<sha256(workspaceKey)[:16]>.md` (`repoNoteId`, lexical like workspace keys). A session still preparing its worktree has none. A deleted worktree's note stays visible, read-only (`sharedNotes.readOnly`), while its record exists; it goes to the trash when the record is dropped. Repository notes are never deleted. Nothing is deleted at startup (orphan files are left alone, so a reset state.json never costs notes).
- **Trash**: `NotesStore.remove(note, label)` moves a note with text to `notes/trash/<date>_<kind>_<label slug>_<stem>.md` (`trashFileName`; rename, else copy and delete); an empty one is deleted. Never read back or pruned. Added after a removed session's notes were lost.
- **Daemon** (`NotesStore`, one per daemon): `load` reads every file into memory at start (after `migrate`, below); `SessionMap.set` projects `notes` (the session note's text, for the existing readers: search, handoff, merge screen, sidebar), `notesFile` (`path`, `revision`, `tooLarge`) and `sharedNotes` (`kind` `worktree`/`repo`, `id`, `path`, `text`, `revision`, `tooLarge`, `readOnly`) into every session, and `persistedSession` strips them (and the worktree markers) before `saveState`. A note change re-sets and broadcasts `session-updated` for every session showing it (`notesChanged`); notes changes never write state.json or bump `updatedAt`.
- **Revisions and conflicts**: a revision is a content hash (`noteRevision`, sha256[:16]; a missing file is the empty text). `save-note` names the revision the UI edited; the store re-reads the file inside a per-note queue and writes only when it still has that revision (atomically: temp file `.<name>.tmp-…` in the same directory, then rename, 0600). Otherwise nothing is written and the response is `{saved: false, session}` with the file as it is. Shared saves also name the note (`noteId` = `kind:id`) so a session that moved to another note is refused. Text is cut at 50 000 characters (`MAX_NOTES_CHARS`); a file longer than that (or over 1 MB) is projected cut with `tooLarge` and refused for saving. Saving the same text writes nothing; saving `''` to a missing file creates nothing.
- **Watching**: a `notify` watcher on each notes directory (non-recursive, so editors that save via rename are seen), per-file debounce of 120 ms, then a re-read in the same per-note queue; a changed revision updates the cache and broadcasts. An event without a file name rescans the directory; a watcher error retries after 1 s. Deckhand's own writes re-read as unchanged, so they never echo. Hidden/temporary files (leading `.`, not `.md`) are ignored.
- **Migration** (`NotesStore.migrate`, daemon start, before `load`): every stored session with a `notes` string gets its file written if missing (an existing file wins); when any stored session still had `notes`, state.json is written again without them. Idempotent; covered by `crates/e2e/tests/notes_daemon.rs`.
- **`open-note`** creates the file (empty, `wx`) if missing and returns its path; the UI opens it with `openInEditor`.
- **UI** (`NotesFlow`): one draft per note key (`session:<id>`, `worktree:<id>`, `repo:<hash>`; a shared note is one draft for every session showing it, so its cursor and unsaved text follow it) holding text, cursor, the last known file text and revision, the save in flight and the editor's scroll. Edits schedule a save 300 ms later; one save per note is in flight at a time (typing during it is saved after it returns); leaving notes focus saves at once, and `E`/Ctrl+O save before opening. An incoming record with a new revision is applied silently when nothing is unsaved (an editor's edit shows up), its own save's echo only updates the revision, and anything else reloads the file and says so (*changed outside Deckhand … your last unsaved edit was not saved*); a refused save does the same. Notes focus turns bracketed paste on (`?2004h`, off on leaving): between the markers Tab and Enter are text.
- **Editor** (`crates/core/src/text_editor.rs`, shared with the JSON editor): `editText` has word jumps and word deletion (Alt+Backspace arrives as ESC DEL via `normalizeTerminalKey`) and, through `EditOptions`, a character limit, Ctrl+A/Ctrl+E as line start/end instead of select-all, Tab left to the caller, and Up/Down/PageUp/PageDown by soft-wrapped rows (`wrapRows`: word wrap at the last fitting space, mid-word otherwise, one column per code point; `moveVisual`, `wrappedEditorLines`, `scrollTopFor`). Checklists (`crates/core/src/notes.rs`): `- [ ]`/`* [x]`/`+ [X]`, indented or not (`parseChecklistLine`); Ctrl+X `toggleChecklist` (adds `- [ ] `, or `[ ] ` after a plain bullet), Ctrl+T `insertChecklistItem` (not Ctrl+N: editors commonly bind it in their integrated terminal), Enter `continueChecklist` (an empty item ends the list). Ctrl+X/T/O/W are plain control bytes, which raw mode delivers unless the host terminal keeps the key (one user's Cursor binds Ctrl+N/E/W/R with `terminalFocus`), so every line/word key keeps a non-Ctrl alternative.
- **Layout** (`notesLayout`, pure): the shared section (header `Worktree · <branch | main checkout> (shared by N sessions)` with `☐ N open`/`☑ N done`, then `deleted, read-only`/`too large` flags), a rule, `This session · <title>`. `budgetSections` gives each body its need when both fit (the session section the rest), else at least 3 rows each and the rest in proportion to what is missing, the focused section's share counting double; tiny panes favour the focused one. An empty section not being edited is one muted line (`No worktree notes · tab to add`). Read mode renders `☐`/`☑` items (checked muted, hanging indent) and bold headings, cut with a muted `+N more lines`; the edited section shows the raw text with an inverse cursor, scrolled to keep it visible. Sidebar details add `☐ 3 open (2 worktree)` (`openChecklistText`; shortened to `(2 wt)`, then without the split) as the first line to go.
- **Terminal editor** (`o` on Notes): `resolveTerminalEditor` (`crates/sys/src/desktop.rs`) takes `$VISUAL`, then `$EDITOR` (split on spaces), else the first of nvim/vim/vi on PATH. The note is saved first, then the UI exits with an edit-note result like an attach, and `run_terminal_editor` (`crates/deckhand/src/ui_loop.rs`) runs the editor on the real terminal with inherited stdio before re-rendering on the Notes tab; the notes watcher picks up the saved file. Vim-family editors source `~/.deckhand/notes.vim` (`-S`, rewritten each launch from `crates/sys/src/notes_vim.rs`): Ctrl+] and Ctrl+Space (the detach keys; Esc can't be, vim needs it) save and `qall`, and in the note's buffer Ctrl+X, Ctrl+T and Enter mirror `toggleChecklist`/`insertChecklistItem`/`continueChecklist` (tested in real headless vim). Ctrl+P is deliberately absent: it would need vim to call the daemon (racing its watcher for the line), and the Tasks view's notes list already sends items. Only a failed launch is reported: vim exits non-zero after any error message seen while editing. A second `-S` sources `notes-status.vim` (`notes_status_vim_script`, in the configured theme's colours), which draws the attach status bar in vim's status line (Neovim's global one, `laststatus=3`) with the session from `$DECKHAND_NOTE_TITLE` and the note keys; vim has no row for a rule there, so the bar's background alone separates it. Other editors get no bar.

#### Tasks (`crates/core/src/tasks.rs`, `crates/core/src/tasks_board.rs`, `crates/ui/src/flows/tasks.rs`; daemon `crates/daemon/src/notes_tasks.rs`)

One task list per repository, beside the notes and deliberately separate from them: notes stay free-form scratch space (their checklists included) and only become tasks when the user sends an item (Ctrl+P in notes focus, `a`/`A` in the board's Notes view, `m` when removing a session whose notes have open items). A single combined "every checklist is a task" model was rejected so that lightweight notes keep working as they did.

- **File and key**: a `tasks` kind in `NotesStore` (`notes/tasks/<repoNoteId(trust root)>.md`), so it reuses the cache, atomic writes, per-file queue and directory watcher. The daemon keys it by `resolveRepoContext(cwd).trustRoot` (`tasksKeyFor`, cached per cwd): the main checkout, so every linked worktree of a repository shares one list. `watch-tasks` sets `ClientSubscription.tasksKey`; changes (ops, or an editor's edit via the watcher) push `tasks-updated` to those clients.
- **Format** (pure, unit-tested): a task is a top-level checklist item, its body the indented lines under it (an indented blank line keeps the body going; a body blank line is written as two spaces). Every other line is kept byte for byte. Bookkeeping is a trailing `<!-- dh:t=<8 hex> wt=<worktree record id> s=<session id> done=<YYYY-MM-DD> auto=merge|done tried=<branch> from=<branch> added=<YYYY-MM-DD> -->` (`META_KEYS`; `tried`: the branch of work dropped unmerged; `from`: the branch an item was left open in when its work ended). Hidden IDs were chosen over a visible `→ branch` because branch names are renamed, reused after a merge, or absent (main-checkout sessions), and so a task can be renamed without breaking its link or a note's `↗` line.
- **Ops, never whole-file saves**: every change is a `TaskOp` (`crates/protocol/src/data.rs`) applied by `NotesStore.modify` to the file as it is on disk inside the per-file queue (no revision handshake: the op is the edit), so concurrent UIs and an editor never overwrite each other. The first op on a file gives every ID-less task an ID; until then the UI addresses such a task by a provisional `~<index>:<title hash>` ID that ops resolve by position (a mismatch throws *no longer in the list*). Clients may send `add` (optionally with a `link`)/`edit`/`toggle`/`remove`/`move`/`assign` (`clientTaskOp`); the daemon checks a client link names work of that repository (`checkTaskLink`: a worktree record that is not deleted, or a session without a worktree record, whose `repoRoot` resolves to the same tasks key). `link`, `tick-linked`, `reopen-linked` and `abandon-linked` are the daemon's.
- **One task per work; its to-dos are steps**: a task linked to work (`wt=`/`s=`) is that work's task (◆), however it got there (`n`, `w`, `add` with a link); a work's other to-dos are the checklist of its note. This replaced follow-up tasks (`assigned=`/`was=`, released at merge), after an audit the user asked for found follow-ups and steps were the same thing twice (two stores, two ways to tick, two rows on the merge screen). `w` onto work with an open task (`hasMainTask`) calls `task-to-note` (`taskToWorkNote`: the task's `↗` line in that note becomes the item again if it is there, else `appendNoteItem` at the end; then the task leaves the list, the note is put back if that fails); onto work without one it is `assign`. `a` in a work's group adds a step (`appendNoteItem` through `save-note`, revision-checked) when the work has its task, else that work's task; `A` adds a backlog task from any row. Items sent from notes always go to the backlog. **Migration** (`migrateFollowUpTasks` at daemon start, after the notes load and before anything writes a task list, since serializing drops the old keys; `migrateFollowUps`, pure): every open `assigned=` task moves into its work's note (a live worktree record's note, or a main-checkout session's own) as an open item with its details, notes written before the list (a crash leaves a duplicate, never a loss); one whose work is gone stays in the backlog; done and released ones only lose `assigned=`/`was=`.
- **Starting from a task** (`create` with `taskId`; top-level sessions only; refused when the task is done or already some work's) stores `SessionRecord.startPrompt` (`taskPrompt`: `<title>: <body>` on one line). It is **typed into the agent's input, never sent** (the user asked to edit before sending; sending it as a first message like a handoff was the first version). After `startWorker`, `WorkerRuntime.draft` waits; each worker `preview-updated` keeps `WorkerRuntime.screen` (a `snapshot` request would resize the agent's PTY, so it is not used). Once the screen has not changed for `DRAFT_SETTLE` (0.7 s, `crates/daemon/src/hooks.rs`; each `preview-updated` restarts it) or on the first `agentStatus` idle (idle needs 5 s without change, which made the first version arrive 2–5 s late), and the screen is non-empty and does not match `AGENT_PROMPT_PATTERN` (folder-trust questions, *press enter to continue*, a `❯ 1.` menu: it waits for the next idle), it writes `ESC[200~<text>ESC[201~` (bracketed paste: no shortcut keys, no submit) and clears `startPrompt`. Agent `input` with letters (escape sequences stripped; Enter or a digit answering a menu does not count) drops the draft, as do `DRAFT_WAIT` (2 min) and the agent's exit (`dropDraft`). One line because Claude collapses multi-line pastes into an uneditable `[Pasted text]` placeholder. Not verified against the real agents: whether each TUI's input is focused at its first idle, and Pi's bracketed-paste handling. `finishCreateSession` links the task to the joined worktree record (`wt`), else to the session (`s`), right after the record is joined (a failed worktree creation leaves it in the backlog).
- **Lifecycle** (daemon): `saveWorktreeRecord` compares the record before/after (`syncWorktreeTasks`): mergedAt set → `tick-linked` auto `merge`; cleared → `reopen-linked` merge; `deletedAt` without `mergedAt` → `abandon-linked` with `tried` = the branch (idempotent, so a record superseded at join is covered). `set-session-done` (`syncDoneTasks`) ticks started tasks with auto `done` when every session of the record has `doneAt`, and un-done reopens auto `done`. `removeSession` abandons the session's `s` link and, when the record is dropped, its `wt` link. `changeLinkedTasks` scans every cached task file for the `wt=`/`s=` needle (a link belongs to one repository).
- **Board** (`tasks_board.rs`, pure): `boardRows` lists a group per work key (`wt:<record>` / `s:<session>`, `linkKey`) with open tasks, in the order its first task appears in the file. A work's only task heads its group itself (`headsWork`: `◆ <title>`, then `workLabel`, `workState` (the lead session's state) and the steps count on the right); a `work` heading row only for a group with no task (`v`) or several (a hand-edited list); then backlog and done. With `scope` (`v`) only that work's group, shown even when empty, and its done tasks. `open(scope)` (`b` passes `workKeyOf(selectedSession)`) puts the selection on that work's first open task. `a` adds to the selection's group (`section` on task rows; the editor head names it). `w` opens a picker in the lower area (`workOptions`: each worktree incarnation / main-checkout session once in sidebar order, skipping deleted worktrees and ones whose sessions are all archived; `pickerRows` shows the backlog and, when `taskOrigin` finds a note still linking the task, `↩ Back to its note` pinned first, then one view, worktrees or main-checkout sessions (Tab/←→ switch; the user found one combined list too long), filtered by every typed word against the label and its sessions' titles). `J`/`K` reorder within a section. Groups (`groupTasks`: in progress = open and linked, backlog, done in the last 7 days newest first, older folded), a task's sessions (`taskSessions`) and the most urgent one (`leadSession`: needs-input/failed/limited while running, then working, idle, exited), the right-hand state (`taskState`). The Notes view (Tab; `noteBlocks`: every note with text, each shared note once, read-only ones left out, grouped by worktree in sidebar order then `main`; `notesViewRows`; `itemsOnly` (`f`) and `scope` (`v`)) replaced a list of open checklist items only, which forced the user to turn every note into checkboxes to see them. `crates/ui/src/flows/tasks.rs` keeps selection by row key, the add/edit editor (title field: Enter saves; body field: Enter is a newline, Ctrl+S saves; Tab switches) and `x`-twice deletion; it renders in the right pane (mode `tasks`), with `TaskBanner` (with `N/M steps`) on a linked session's Notes tab.
- **Steps** (`workNote`, `noteSteps`, `boardRows(…, stepsOf)`; UI only): the checklist of a work's note (`wt:`: the worktree's shared note from any of its sessions, non-archived first; `s:`: the session's own) is listed as `step` rows under the work's task, which carries `steps` (done/total). Space saves the note with `toggleChecklistLine` through `save-note` (revision-checked; a refused save says so); a read-only (deleted worktree) note refuses. Nothing is stored: the note is the only copy. Syncing items and tasks both ways was rejected as too fragile with notes edited in editors.
- **New-session form from a task**: `n` on a backlog task (`startFromTask`) opens pick-program → enter-name with the name (cut to 64 at a word), a `new` worktree and `taskStart`; Esc in the picker returns to the board. In enter-name with a new worktree, ↑↓ cycle `baseOptions(list-branches)`: the `worktree.branchFrom` setting first, then local branches by last commit. `baseBranch` reaches `createWorktreeForSession` → `chosenStart` (a local branch, or `origin/<name>` as last fetched, never fetching), replacing `branchFrom`. An existing branch with the worktree's name is reused, ignoring the base.
- **Notes → tasks**: `promote-note-item` (section, line, revision, noteId as for `save-note`) refuses a stale revision, a non-item or a ticked item, adds the task first (to the backlog), then saves the note with the line replaced by `- ↗ <title> <!-- dh:t=<id> -->`, removing the task again if that save is refused. The notes UI flushes the draft before sending and maps the cursor to the line. `send-open-items` (`A` in the Notes view; `promoteOpenNoteLines`) does the same for every open item of a note at once. Read mode renders `↗` lines with the task's state from the list (`taskLinkLookup`, `taskLinkSuffix`: `· in Tasks`, `· done`, `· not in Tasks`; nothing claimed before the list loads); edit mode shows them raw.
- **Tasks → notes** (`return-task-to-note`, `↩ Back to its note`): the daemon finds the note holding the task's `↗` line (`taskOrigin`), refuses a done task, a started one, a read-only note or none, saves the note with the line turned back into `- [ ] <title>` and the details indented under it (`returnTaskToNote`, revision-checked), then removes the task (restoring the note if that fails). Tasks moved out of a removed session's notes have no `↗` line, so they cannot go back.
- **End of work**: `merge-worktree`, `kill` (with deletion) and `delete-worktree` take `sendOpenItems`; the daemon sends the worktree note's open items to the backlog (`sendWorktreeItemsToBacklog`: no link, `from` = the branch) after a clean merge (`result.sentItems`; not for conflicts), before removal on exit, and in `W` after the re-check (or at once for a missing worktree). The UI offers it whenever the note has open items (`worktreeOpenItems`), on by default: a selectable row on the merge confirmation (`MergeFlow.keepOpenItems`), a line and Space on the kill confirmation (`killKeepOpenItems`) and on W's (`DeleteConfirm.keepOpenItems`); W rows tag `☐N`. Merge detection and `M` do not move them. `remove` with `moveOpenItems` (Backspace on an archived session → `confirm-remove` → Enter) adds the open items of the session's note and, when it is the last session of its record, its worktree note's, with `from` = the branch.
- Tests: `crates/core/src/notes.rs`, `tasks.rs` and `tasks_board.rs` (pure); `crates/e2e/tests/note_items_daemon.rs`, `steps_ui.rs`, `tasks_daemon.rs`, and W's confirmation line in `worktrees_ui.rs`.

#### Git tab: the Changes view (`crates/core/src/changes_model.rs`, `crates/sys/src/changes_git.rs`, `crates/daemon/src/changes.rs`, `crates/ui/src/flows/changes.rs`, `crates/ui/src/panes/changes.rs`)

The Git tab shows the workspace's changes like VS Code's Source Control panel; lazygit is only attached (`o`). No worker or PTY: the daemon runs Git in the workspace root.

- **Model** (pure, unit-tested): `groupChanges` turns porcelain-v2 entries (`parseStatus(...).entries`, `crates/sys/src/workspace_git.rs`; `StatusEntry` = kind, XY, path, origPath) plus numstat (`parseNumstat`, renames keyed by the new path; a conflict's doubled combined record keeps the last) into groups in VS Code order: `conflicts` (`u` records, letter U, `conflict` = XY), `staged` (X ≠ `.`; R/C keep `origPath`), `unstaged` (Y ≠ `.`; so a partially staged file is in both), `untracked` (`?`), sorted by path, capped at `MAX_CHANGES` (2000) in group order with exact `counts` and per-group `omitted`. Also `changeRows` (headers/entries/"+N more"), `reselect`/`groupOffset` (selection by (group, path); if gone, the same offset within that group, else the first entry below an emptied group), `stageMode`, `changeLabel` (name first, `old → new`), `firstChangedLine` (new-side line of the first change in the first hunk, combined `@@@` diffs included; 1 without a hunk), `classifyDiff` (meta only before a file's first hunk; one prefix column per parent) and `untrackedDiff`.
- **Git I/O**: `readChanges` = `git --no-optional-locks status --porcelain=v2 -z --branch --untracked-files=all` + `diff --cached --numstat -z -M` + `diff --numstat -z` in parallel; untracked line counts from the files themselves (lstat, regular files ≤ 1 MB, first 500, NUL sniff for binary, cached by size+mtime per workspace). Throws *Worktree directory is missing* for a gone directory. `readChangeDiff`: bounded spawn (256 KB, then cut at the last newline; 8 s timeout): staged → `diff --cached -M -- <orig> <path>`, unstaged/conflicts → `diff -- <path>` (combined for conflicts), untracked → file read (symlink: its target; directory: nothing; binary sniff), all with `--literal-pathspecs --no-color --no-ext-diff`. `applyStage(cwd, snapshot, mode, target?)` validates against a fresh snapshot (a target must be listed on the matching side, else *not among the staged/unstaged changes*), then: stage = `git --literal-pathspecs add -A --pathspec-from-file=- --pathspec-file-nul` (paths NUL-separated on stdin; deletions and conflict resolution included); unstage = `restore --staged` the same way (both paths of a rename), or `rm --cached -r -q --ignore-unmatch` without HEAD; stage all = `git add -A`, except with conflicts present: the unstaged/untracked paths only (`skippedConflicts` reported; mirrors VS Code's confirm-before-staging-conflicts); unstage all = every staged path (never `git reset`, which would also drop MERGE_HEAD). Pathspec-from-file needs Git ≥ 2.26.
- **Daemon** (`changeWatches`): `watch-changes` stores `watchedChangesSessionId` on the client, `syncChangeWatches` polls exactly the workspaces some client watches (`CHANGES_POLL`, 2 s, skipped while a read is queued or running) and forgets the rest; it runs on watch, client disconnect, `saveSession` (sessions joining/leaving a workspace) and session removal. Every Git run of a workspace (status, diff, stage) goes through its `queue` (no overlap); `refreshChanges` shares a read that is queued but not started, stores `last`, and `publishChanges` sends `changes-updated` (stamped with each watcher's session ID and `workspace`) to every client watching any session of the workspace, only when the record's JSON changed. A failed read (cleanup in progress, directory gone, not a repo) becomes a record with `error`. `changes-diff` reuses a status read younger than 2.5 s to validate (group, path). `change-stage` re-reads status inside the exclusive section, applies, refreshes (pushing to every watcher) and responds `{changed, skippedConflicts, changes}`. Kill-with-delete stops the workspace's watch before removing the worktree; daemon cleanup stops all. Errors for sessions without a workspace use the Git pane label (*Git is unavailable: …*).
- **Committed group** (not in the TS, v49): `committed` entries follow the status groups: the files `diff --name-status`/`--numstat -z -M <merge-base> HEAD` name, where the merge base is that of HEAD and `CommittedBase`: the session's `worktree.baseRef`, else `DefaultBranch` (`resolve_default_branch` local, else `origin/HEAD`), because worktrees made by a creation script or attached with the picker record no `baseRef` (most of them in practice). Only for a worktree (`mode` ≠ `none`); the daemon notes the base of the session viewed on the workspace's watch, `ChangesWatch.base`. `read_committed` caches the result in `ChangesCache.committed` keyed by HEAD and the base's SHA, so the 2 s poll re-runs only `rev-parse`; a base that names no commit (or HEAD on it) means no group. `ChangesSnapshot.merge_base` is what `changes-diff` diffs a committed file against (`diff -M <merge-base> HEAD -- [<orig>] <path>`); `apply_stage` refuses committed targets and the UI's `space` says the file is already committed. `ChangeCounts.committed` is left off the wire while 0, so older records and the TS-recorded fixtures read and write unchanged.
- **UI**: `crates/ui/src/app/` owns the record (`watch-changes` while the Git tab is shown, `watch-changes` without a session when leaving it, `changes-updated` filtered by the selected session) and mode `changes-focus`; `ChangesFlow` owns selection, the debounced (60 ms) diff fetch (refetched when the record changes) and the focus keys; `panes/changes.rs` renders a header (workspace path · branch, counts), the list (browse: from the top with "↓ N more"; focus: windowed around the selection with its group header), and in focus the diff (side by side from 100 columns of pane width, else stacked under the list). `o` on the Git tab is ready once the Changes record confirms the workspace (lazygit starts on attach). Enter/`E`: `openInEditor(file, onError, line)` (`crates/sys/src/desktop.rs`: `-g <abs>:<line>` for the cursor/code CLIs; the macOS `open -a` fallback ignores the line); a file missing on disk gets a status message instead.

## Design rules

- Keys (redesigned on `feat/tasks`; the reasoning and the before/after of every key were reviewed with the user; the full list is [docs/keys.md](docs/keys.md)): (1) two places, the session list and the pane: `→`/`l` steps into the pane, `←`/`h`/Esc back out; (2) `enter` does the main thing (on a session: open it full screen, the same as `o`); (3) one verb per key on every screen: `space` toggles or marks done, `a` adds, `x` removes or stops (asking first), `E` opens your editor, `o` goes full screen, `r` runs; (4) uppercase is the stronger variant of its lowercase (`n`/`N`, `x`/`X`, `s`/`S`, `m`/`M`) or a rarely visited screen (`C`, `G`, `H`, `A`, `R`, `T`); (5) tab letters `p t g d a` switch tabs (`D` starts or stops Dev); (6) lists move with `j`/`k`/arrows, `g`/`G`, PgUp/PgDn, and search only after `/` (sidebar, help, the Tasks `w` picker, the existing-worktree picker): while typing, letters are text and ↑↓ still move; Enter keeps the search and gives the letters back, Esc clears it; (7) anything that loses work asks first; `X` asks too (with the force kill chosen) and never deletes, and `S` asks for a second press; (8) a key that can't act says why (`m`/`M` without a worktree, `x` on an exited session) rather than doing nothing; (9) jumping to a session from the board or `W` (`goToSession`, `onOpenNote`) goes through `revealSession`, which clears the search, widens a filter that hides it and expands its collapsed or hidden ancestors, because `selectedSession` only resolves among `visibleSessions` (otherwise the selection fell back to the first listed session). Exceptions kept on purpose: `J`/`K` scroll the diff in the changes view (nothing to reorder there); `a` is the Notes tab in browse and "add" in lists (they never meet). Ctrl+A/Ctrl+E are line start/end in every one-line field; select-all exists only in the raw JSON editor. Every keymap entry (`crates/ui/src/keymap.rs`) names its guide line or why it has none, and the keymap tests (`undocumented_in_guide`) fail when a key has no line in `crates/core/src/help.rs`.
- Mac keyboards have no PgUp/PgDn or Home/End (Fn+arrows, which Terminal.app keeps for its own scrollback), so every page or top/bottom move also has a letter: `J`/`K` page (dialogs and the merge screen via `keymap::SCROLL_DIALOG`, the details views `i`/trust review/DELETE prompt in `scroll_details`, the guide, Settings lists by 5, the Changes diff) and `g`/`G` go to the first/last (lists, the guide's topics, Settings lists; not in `i`, where `g` is the Git tab). Not added: the notes editor's Ctrl+Home/End (letters are text there) and a second detach key in the hint (the user declined). Ctrl+Space, the main detach key, is macOS's input-source switch when more than one input source is set up; Ctrl+] still works.
- Lifecycle and activity are distinct; do not overload lifecycle status to mean activity:
  - lifecycle `status`: `starting`, `running`, `exited`
  - activity `agentStatus`: `unknown`, `active`, `idle`, inferred from visible preview changes, not agent hooks. Resize-only redraws must not mark idle agents active. `active` needs a sustained run of changes (`ACTIVE_AFTER`, 1 s, no gap over `ACTIVE_MAX_GAP`, 0.5 s: `sustained_change` in `crates/worker/src/session.rs`); changes within `INPUT_ECHO_WINDOW` (0.5 s) of input are its echo and only re-arm the idle timer (`last_input_at`); any other change re-arms it, so a single change still settles to `idle` after 5 s (the daemon's stale-working check relies on that). `agentStatus` is persisted only on transitions, to avoid excessive disk writes.
- Agent signals: lifecycle hooks (on for Claude unless `agent_hooks: false`; `hooksEnabled`) set a separate advisory `attention` field, with an in-memory `reason` (`AttentionReason`: what the session asks or said; `normalizeHook` builds it from the subset `hookPayloadFields` forwards; `persistedSession` strips it). A question/plan tool's `PreToolUse` is needs-input, not working; a Notification's generic text never replaces an existing reason; `permission_prompt`/`elicitation_dialog`/`elicitation_url_dialog`/`agent_needs_input` are needs-input (Claude sends them once a prompt has waited ~6 s untouched, each keystroke deferring them; `permission_prompt` is the only signal of a sandboxed command's network request, which runs no PermissionRequest hooks); `idle_prompt` (a reply ~60 s old, nothing typed since) is response-ended, never needs-input, and only replaces working/unknown (`AgentSignal.idle`), since it made every finished session read *needs you*; Enter, a digit or a lone Esc typed into the agent (`answersPrompt`; not arrows, the mouse wheel, letters or a paste) while it needs input makes it working (`markAnswered`, event `Answered`) and drops hooks that started earlier, because Claude sends nothing between allowing a tool and its PostToolUse (minutes for a long command; reported as sessions stuck in *needs you* while they worked); a native subagent only reports permission prompts, and its tool use only clears a needs-input; signals carry the hook's `sentAt` and one older than the last applied (`WorkerRuntime.lastHookAt`) is dropped, since Claude's hooks are `async`; a `working` attention becomes `unknown` (`ScreenIdle`) when the screen goes idle (`setWorkerAgentStatus`), because Esc sends no hook. Shown by `attentionReasonLines` (details block, Tasks board details) and in notifications (`attentionMessage`).
- Terminal, Git and Dev belong to the workspace, not the session: gate them on "has a workspace" (`workspaceKey`, plus the daemon's *not ready* record), never on "is running"; agent exit must not stop or detach them.
- Merge/deleted markers of a linked worktree belong to its worktree record: write them with `saveWorktreeRecord`, never onto a session (the session copy is a projection and is not persisted).
- Notes live only in their files: `notes`, `notesFile` and `sharedNotes` on a session are projections the daemon recomputes on every set and strips before persisting. Write notes with `NotesStore.save` (revision-checked), never by setting them on a session.
- Preview (and the Terminal tab's shell) is a plain-text snapshot, except in Preview focus (`→` on a running session) or terminal focus (`→` on a shell), where it is interactive: every key goes to the agent through the daemon's `input` (no attach, no resize, since the agent PTY is already the preview's size) and the Preview draws the agent's styled screen and cursor. Only that UI gets the styled screen (see *Preview focus: typing to the agent*). Attach (`enter`/`o`) is still there for full-screen use: it leaves the ratatui UI and hands stdin/stdout directly to the selected PTY (`ui_loop`), then re-renders.
- PTY sizing is per PTY: Preview sizes the agent PTY to the preview viewport; Terminal/Dev/action size their shared workspace PTYs to the pane viewport of the last viewer (last watch/resize wins); lazygit is sized by its attach; attach sizes the active PTY to the full terminal less the status line; returning from attach reapplies pane sizing.
- Colours follow the user's terminal: the theme is ANSI named colours on the terminal's background (`TERMINAL_THEME` in `crates/ui/src/theme.rs`). The design system's dusk palette (`docs/brand/deckhand-design-system.html`, `DUSK` in `crates/core/src/display.rs`) is an opt-in (`"theme": "dusk"` in `config.json`) for recording demos and screenshots, not the default: tried as the default, its fixed slate background and pastel text looked worse in a real terminal than the terminal's own theme, and clashed with the agents, which draw in the terminal's colours. In dusk mode `apply_dusk` (run last in `render_app`) resolves what the terminal would decide: default background and text (plain text in `--muted`, bold in `--ink`), inverse as a fill with `--ink-dark` text, dim as a fade toward the background; `draw_border` fills boxes, and the attach status line has its own dusk colours. Keep both modes working when changing colours: use `THEME` roles and the Ink colour names `theme.rs` maps, never fixed colours in panes.

## UI behaviour

### Layout and indicators

- Sidebar layout (`crates/core/src/sidebar_model.rs`, pure and unit-tested; `crates/ui/src/panes/sidebar.rs` renders): a row is `<cursor><number> <tree><status> <title> … <markers> <agent>`. The cursor column is the frame's left padding column (`›` on the selected row). Numbers carry no brackets, are right-aligned to the widest and dim unless selected. Example (width 34):
  ```
  │ Sessions         all 7/7 · ! 2 │
  │╎ 1 ▾ ⠋ auth refactor       ▶ ✶ │
  │› 2   ↳ ● write tests         π │
  │╎ 3   ⑂ ○ try alt approach    ✶ │
  │  4 ? fix flaky checkout e2e… ◇ │
  ```
- Sections by state (not in the TS; the default view, `V` switches to your own order and back; `sessionView` in ui-state.json, written only as `"order"`): `crates/core/src/session_sections.rs` puts each session in one of Needs you (running and asking, failed or limited, as `urgency` 3), Unread (running, turn over, reply unread), Working (starting, or `agentStatus` active, even with an older reply unread), Idle and Exited, listed in that order under a header row (`  Idle 3 ───`, `ListLine::Header`; empty sections have none). `order_by_section` keeps the sidebar order inside a section and rebuilds the tree there: a sub-session is indented under its parent only when both are in the section, otherwise it sits at the section's top level with its `↳`/`⑂` (the user asked for that over keeping families together); `SidebarRowsInput.sectioned` computes depth, `▾` and `+N` over the session's section. A sub-session at depth 0 whose parent is among the sessions (another section, a search, the parent not listed) names it after its title (`RowRole::Parent`, ` · parent`, muted, only in the room the whole title leaves, at least 4 columns of it; `SidebarRowsInput.parent_names`, off in the TS parity replays; never counted when the sidebar is measured), and `session_details_with_parent` adds `↳ sub-session of <parent> · <its state>` (`⑂ fork of` for a fork) after the location, so `DETAIL_ROWS` is 10. The user found separated sub-sessions hard to place without it. `App::visible_of` does the grouping, so `j`/`k`, the numbers and `!` follow it; collapse (`c`) is not applied in this view (`collapse_applied`) and `c` says so. A list window that starts inside a section shows that section's header in place of its first row (`window_lines`, three rows or more), and the `↑ N more` count includes the row it replaced. `J`/`K` still move the session among its siblings in `sidebarOrder`, which shows inside a section. `c` there folds the Exited section instead (`BrowseState.exited_collapsed`, `exitedCollapsed` in ui-state.json, written only when true; `App::exited_folded` applies it only in the active view without a search, as `collapse_applied` does): `visible_of` drops Exited sessions but the selected one (a session that exits under you stays until you move off it), and `list_lines` keeps the Exited header, with the whole count from `folded_exited_count` and `▸` (`▾` when open), last even when none of its rows is listed.
- Status glyph before the title (`statusGlyph`): spinner for starting/active/working, green `●` idle, yellow `◌` running with unknown activity, gray `○` exited; with agent signals `?` needs input, `◆` response ended, `!` failed (also failed/interrupted exits), `⌛` rate-limited.
- Tree: sub-session rows are indented two columns per level (up to 4); clean children show `↳`, forked `⑂`; parents show `▾` / `▸` (expanded/collapsed, `c`). Rows without children carry no placeholder column. The tree (`▾ ▸`, `+N`, `c`) counts only the sub-sessions the current filter lists, so an archived one leaves its parent childless in the active view; the details' `╎N` and the Notes header's `shared by N sessions` skip archived sessions too.
- Right-hand suffix, in order: `▶` Dev running, `▣` archived, `!` cleanup error, `✓` merged (the worktree's marker), `☑` done (`doneAt`, `DONE_MARKER`), `+N` collapsed/hidden sub-sessions, `↑` outdated (dim: a running session whose `agentVersion` is older than its agent's installed version, `sessionOutdated`), then the agent glyph (`✶` Claude, `π` Pi, `◇` Codex) last. When the title would get fewer than 4 columns (or fewer than it needs), `↑`, `+N`, `✓`, `☑`, `▣`, `!` and `▶` are dropped in that order; the agent glyph stays.
- Workspace awareness: `devRunning` mirrors the workspace, so `▶` is shown once per workspace, on its first row on screen; sessions without a workspace key keep their own. Rows on screen sharing the selected session's workspace get a dim cyan `╎` in the cursor column.
- Dimming: archived rows are dimmed (title and glyphs; `▣` and `☑` stay readable) in every filter except `archived`, which lists only archived sessions: unlike the other filters (and search) it brings no parents along for context, since a live parent there counted as archived, took Backspace (archiving it) and puzzled the user; an archived sub-session of a live session is top level there (`sessionDepth` over the listed sessions). Done rows not dimmed by those rules get `SidebarRow.done`: only their title and tree are muted (gray, not dim), so the status glyph keeps its colour and `☑` stays readable. The selected row is never dimmed.
- Header (`sidebarHeader`): `Sessions` left; right the plain row count in the default view, otherwise the filter and/or `/query` with `shown/total` highlighted in cyan; then `· ! N` (yellow) when N non-archived sessions are blocked on you (`session_blocked`: asking, failed, rate-limited, exited failed or interrupted) and `· ◆ N` (accent) for the others with an unread reply (`session_has_unread_reply`); the TS counted both as one `! N`, which hid a finished reply among the interrupted sessions. `!` still cycles both kinds (`sessionNeedsAttention`). A running session with an unread reply draws its `◆` in the accent colour (`status_color`) and its title bold (`SidebarRow.unread`, not on the selected or dimmed row) until you attach; the details, the Tasks board and the preview badge say `unread reply` (`status_words`, `status_label`). Read state lives in the daemon, not ui-state: the session's `replyReadAt` (set by `set-reply-read`), and the reply that ended the last turn is read when `attention.at` is not after it (`with_reply_read`, which fills the UI-only `replyRead`). Detaching from the agent sends `set-reply-read` read (`ui_loop::record_reply_read`); `U` toggles it (`toggle_selected_reply_read`; only on a session whose last turn ended). ui-state's `readReplies` is legacy: still normalised and written back, never consulted, so replies read before this change showed unread once. Narrow widths drop the title first, then cut the filter/search, keeping the count and `! N`. The app header does not repeat filter/count: its second row is the repo path at full width (while the filter menu is open, the footer lists its keys).
- Details block (`sessionDetails`): pinned to the bottom of the sidebar in the rows the list leaves free. A list longer than the sidebar keeps as many rows as the largest details block of any listed session (at most `DETAIL_ROWS`, 9: rule, two title lines, state, two lines of why it waits, location, task, checklist), so the list keeps its size as the selection moves, and scrolls in the rest between an `↑ N more` and a `↓ N more` line (`moreText`: adds `· ! N` in yellow when hidden sessions on that side need you; both lines stay, blank when empty, so rows don't jump); only when the sidebar has at least `DETAIL_MIN_SIDEBAR_ROWS` (21) rows, so tiny sidebars stay all list. Before, a long list (80 sessions in one repo) never left room, which read as "the details only work for new sessions". Contents: the full title (two lines with five free rows, else one, ending in `…`); `<agent glyph> <agent> · <state in words> · <age>` (an outdated session first tries `✶ claude 2.1.287 · 2.1.290 installed · …`, then `✶ claude 2.1.287 → 2.1.290 · …`, then without the name and the age; `statusWords` mirrors `statusGlyph`; the age counts from the attention signal while running, else `agentStatusUpdatedAt`, which is also set at exit; narrow widths drop the agent name, then the age); why it waits (two lines when the location still fits after them); the location: `⎇ <branch>` (a sub-session without its own branch takes one from a session sharing the workspace), `main checkout`, `worktree deleted` or `preparing worktree`, then the markers as glyphs `╎N` (N others share the workspace), `▶`, `✓`, `☑2d` (`doneGlyph`), `▣`. The markers were words (`shared with 2 · ▶ dev · merged`), which never fitted a usable sidebar width; now a long branch is cut to keep them, and only when the branch would get fewer than 8 columns are markers dropped from the end. Fewer rows drop the checklist line first, then the location; fewer than three, or no selection, hide the block. Only session data is used (no daemon requests, no Git). The ages need a clock: the app renders with the current time and, when no spinner is animating, schedules one render exactly when the first shown age would change (`ms_until_age_changes`).
- Sidebar row numbers are positions in the list. With 10 or fewer visible sessions, single digits jump immediately and `0` selects row 10; with more, numeric input is briefly buffered for multi-digit selection (`enter` confirms at once).
- Right pane is one rounded bordered frame with a tab bar; sub-panes are borderless content containers. The tab bar marks Dev green with ` ●` while it runs and Notes with ` ☐ N` while the notes it shows (the session's and the shared one; a deleted worktree's read-only note left out) have open items (`TabBadges`, `open_note_count` in `crates/ui/src/panes/tabs.rs`). No other badges: Changes and the action are watched only while their tab shows, so a Git or Terminal badge would be stale.
- Dialogs (`Mode::is_dialog`: new session and its worktree picker, the run list, kill and remove confirmations; the `W` delete confirmation over its list) draw over the right pane instead of replacing it: the pane behind is rendered and faded (`dim_area`), and the dialog is cleared over it (`draw_dialog`, `DialogRows`, `DialogView` in `crates/ui/src/primitives.rs`). Ink had no z-order, which is why these replaced the pane in the TS. Rules, from the user: no dialog may hide what the old full-pane screens showed, none may be bigger than its content needs, and none may resize as you use it (switching the workspace mode, moving a selection, typing a filter, going from picking the agent to naming the session).
  - Size: `draw_dialog` lays its rows out at the widest width (the pane less 2 columns each side, at most 120), then at the width its widest row needs (at least 60, `dialog_fit_width`), keeping the narrower layout only when every row reads the same (wrapping and cutting measure ☑ and → wider than `string_width`); its height is its rows, border and a blank row above and below (dropped when the content would not fit with them), at least 10 rows and at most the pane less a row above and below (`dialog_height`). It never shrinks while open (`DialogView` floors: the last drawn size, in `App.dialog`, reset when another dialog opens, picking the agent and naming the session counting as one; `WorktreesFlow.confirm_scroll`), so it can grow once when details arrive after it opens. The run list is as tall as its tallest row's details need. Tried and rejected first: a fixed two-thirds-of-the-pane minimum (big and empty on a tall terminal) and a full-height size for long dialogs (tall and empty).
  - Content is a header (the question, kept in view), a body that scrolls with `J`/`K` or PgUp/PgDn past the tallest height, except while a field takes letters as text (the session name, the worktree picker's search, typing DELETE) (`keymap::SCROLL_DIALOG`, `dialog_scroll`; the border shows `↑ N more · K` / `↓ N more · J`), and a footer (choices and key hint, kept at the bottom). Nothing is cut to fit: every lost file (up to the 100 an inspection names, `CLEANUP_FILES_LISTED`), conflicted file, bulk-deleted worktree and open item is listed, and merge notes and a failed hook's output wrap in full.
  - Full screens stay full: Tasks, Settings, Agents, Help, the `W` list, and the scrolling details views (`i`, trust review, the DELETE prompt). The merge confirmation and its conflicts screen went back to the full pane after trying them as dialogs (the user agreed): merge is a review (commits, notes, warnings) that wants all the room, and as a dialog it grew when its preview loaded; conflicts follows it. They keep the header/body/footer rows and `J`/`K` scrolling (`Mode::scrolls_body`, `draw_panel`).
  - Rule for every confirmation that loads after it opens (asked for by the user after the merge choices jumped): no choices until what they depend on is in; only Esc acts meanwhile and Enter says it is still checking. Merge waits for its preview or its error (`merge_loading`); kill waits for the worktree check and, when the branch could go too, the branch check, unless the worktree's deletion is already blocked (`kill_loading`); the `W` deletion waits for both checks of one worktree (`WorktreesFlow::confirm_loading`; bulk and missing worktrees check nothing). Kill and `W` deletion show the worktree's or the branch's check depending on the selected choice, so they open at the size of the bigger of the two (`dialog_view_fitting`). The run list (`r`) opens only after the action's and Dev's running states are in (`open_run_list`, busy meanwhile).
  - Pane snapshots (`fixtures/ui/panes`) show the dialog in its 98x31 pane; `fixtures/ui/07-dialog-over-dashboard.txt` shows one over the dashboard.
- The terminal title is `deckhand · <repository>` (`terminal_title`, `sync_terminal_title` in `crates/ui/src/app/effects.rs`; the user did not want the `! N` counts in it). The first write pushes the terminal's own title (XTWINOPS 22) and unmount pops it (23); an attach sets its own title in between.
- Footer messages stay one row; an error too long for it also shows whole (wrapped, line breaks kept, at most 8 rows) in a red box at the top right of the content while the footer shows it (`error_toast_rows`): the top, so the preview's latest lines, where an agent asks for input, stay in view.
- Frames: the UI uses every terminal row (the TS kept a spare row below the footer because Ink repainted the whole screen once its output reached the terminal height). Updates are drawn at most once per 34 ms, but a key (not a mouse report) draws at once. After a resize the clear and the repaint go out in one synchronized update (`InkBackend::clear_region` in `crates/ui/src/app/event_loop.rs` opens it), so the empty screen never shows.

### Controls: implementation notes

Every key is in [docs/keys.md](docs/keys.md); this is what the keys go through and why some work the way they do. Browse mode is `crates/ui/src/app/modes/browse.rs`.

- Typed work (keyboard audit): Esc in the task editor saves (`editor_input`; an empty title, or an edit that changed nothing, just closes), as the notes editor does. A first Ctrl+C in any text field acts as Esc (`App::typing_in_field`: searches, the new-session name and worktree search, DELETE prompts, the notes and task editors, the task picker's search, the guide's search; Settings keeps `SettingsFlow::cancelable`). Leaving the UI (`exit_with`: quit or attach) saves every unsaved note first (`NotesFlow::flush_all`) and waits up to `REORDER_EXIT_WAIT` for it, as for sidebar moves.
- Typing focus safety (keyboard audit): while keys go to an agent or shell, the sidebar dims all but the selected row (`SidebarProps.typing`), and the pane header's badge is filled and never the part cut (`typing to the agent`, `typing into shell N`). When focus ends by itself (`interactive_focus_effect` → `end_focus`: the agent exited, the shell closed, the selection or the connection went), `PreviewFocusState.held_since` holds session-list keys until `TYPING_ENDED_QUIET_MS` (750 ms) pass with no key, measured from the last key held (`hold_key`, in `App::on_key`); Ctrl+C is never held. The first Ctrl+C of each stint (`ctrl_c_hinted`, reset on leaving) says it went to the agent; it is still sent. `detach_position` also reads Ctrl+] and Ctrl+Space as CSI-u (`ESC [93;5u`, with `:alternates`, `:event` and the Caps/Num Lock bits) and modifyOtherKeys (`ESC [27;5;93~`) presses, so an attached TUI that turns those keyboard modes on can't swallow the detach key.
- Reach (keyboard audit): Ctrl+letter is never the letter outside a text field and Settings (`App::handle_input`: Ctrl+X opened the stop confirmation, Ctrl+A the Notes tab, Ctrl+D armed Dev), except Ctrl+D / Ctrl+U, which are turned into PgDn / PgUp there, so every screen that pages pages with them; the session list and the Tasks board move half their list on them (`pane_inner_height / 2`, `TasksFlow.list_rows / 2`). `;` does what `!` does (home row, no Shift). `h` and `←` go back on Tasks, Worktrees, Agents and the run list, as Esc does. ↑/↓ and Ctrl+N / Ctrl+P move while typing the session search; Ctrl+N / Ctrl+P also pick the new worktree's base and move in the existing-worktree picker. Digits arriving as one chunk (`"12"`) go through the number handling one at a time. Esc in the stop confirmation's DELETE prompt goes back to the choices, as in Worktrees. Agents re-checks with `R` (was `r`), and a failed update's status says `G shows the output` (it named `U`, which did nothing).
- Press twice (`crates/ui/src/press_again.rs`, `PressAgain`): the one rule for a key that is hard to undo but not worth a dialog. The first press arms its target and the status line says what a second one does (`x again stops build`); the same key on the same target within `PRESS_AGAIN_MS` (2 s) acts, and any other key or the wait running out cancels (handlers `take()` it first). Used by the run list's `x` (on its row key), the Tasks `x` delete and Git changes `a`/`A` (only while a file is partly staged: `changes::partly_staged`). From the keyboard audit (`docs/future/keyboard-audit.md`), which asked for one convention rather than several.
- Run list rows (`handle_pick_action`): one rule for Dev, Dev processes, actions and shells. Enter starts what is stopped and shows what runs on its tab (Dev tab, the action's or the shell's Terminal view), back on the session list; `x` twice stops the selected row only (the running action from its own row, now marked `● running`; before, `x` stopped it from any row and Enter on running Dev stopped it), closes an extra shell or restarts the first one. Restarting anything else is `x x`, then Enter.
- `D` starts or stops Dev from any tab and shows the Dev tab (`run_dev`, the same review gate as the run list; Esc from that review returns to the session list); `d` only shows the tab. History: "`d` on the Dev tab starts it" (a later second `d` started servers by accident), briefly Dev only via `r` (clumsy), then `d` twice within 500 ms, which key repeat on a held `d` could fire and which the keyboard audit replaced with `D` (`docs/future/keyboard-audit.md`). Switching sessions restores that session's last tab, defaulting to Preview.
- Stepping into the pane (`stepIntoPane`): Preview → `preview-focus` (running sessions; it records `preview_focus.session_id`, the session the keys go to, and clears any stale styled screen), Git → `changes-focus`, Notes → `notes-focus`; on Terminal and Dev it says Enter opens them. A Preview whose agent is not running says *nothing to type to: s resumes it*.
- `enter`/`o` open full screen what the tab shows, also for exited sessions with a workspace. A finished action cannot be attached (*r runs an action again*); Dev that is not running says *r starts it*; a non-running session on Preview says *s resumes it*.
- `v` on the Terminal tab switches between the shell and the worktree's last action (`terminalView`). The Terminal header reads `shell │ <name> ● running` (or `✓ exit 0`, `✗ exit N`, `✗ signal N`, `○ stopped` after a worker crash) (`actionStatus`, `hasAction` in `crates/ui/src/panes/terminal.rs`). The view is kept across attach/detach (an `Rc<Cell<TerminalView>>` in `crates/deckhand/src/ui_loop.rs`, passed as `initial_terminal_view`) but not across UI restarts.
- `E` uses the `cursor`/`code` CLI, macOS fallback `open -a Cursor` (`openSelectedInEditor`).
- `r` (mode `pick-action`, `crates/ui/src/app/modes/action_picker.rs`): row 0 is the worktree's Dev command when the session has a workspace (`runListHasDev`; Enter, or `x` while it runs, calls `runDev`), then the actions. While an action runs, `x` stops it and running another is refused (*The <name> action is still running; stop it first (r, then x)*). Opening the list re-watches the action.
- `N`: the picker lists the agents, then `⑂ Fork parent` (Claude/Pi parents), then `↳ From its handoff (H)` when the parent has `handoffPath`; choosing that sets `handoffFromId` and the picker asks for the agent.
- `x` (`confirm-kill`): a session without a worktree gets just *Kill session* / *Cancel*, no cleanup inspection; `X` opens the same confirmation with only *Force kill* / *Cancel* (`open_force_kill_confirm`, `force_kill_options`; no cleanup inspection) and never deletes a worktree; it acted at once before the keyboard audit. Workers send SIGTERM first and SIGKILL after a short delay. `x`/`X` on a starting session cancel startup.
- `f` (mode `pick-filter`, `crates/ui/src/app/modes/filter.rs`, lines from `filterMenuLines`, `SESSION_FILTER_KEYS`, counts from `sessionFilterCounts` with the current search, computed only while open): moving sets the filter live; Esc restores the filter and selection it was opened on (`filterMenuBack`). `fr`/`ff` arriving as one chunk is handled in browse. It replaced a fixed cycle (active → archived → all → attention → running → exited) that the user found slow.
- Backspace archives an exited session; on an archived one it removes it after `confirm-remove` (`requestRemove`), always: removal used to be the first Backspace (the user wanted finished sessions archived rather than deleted), and the confirmation used to appear only with open items, so a second Backspace meant to archive removed the session at once (found in a key-binding audit).

### Preview focus: typing to the agent

The user wanted to use agents without attaching: answer a prompt, approve, type a line, without leaving the UI or resizing the agent. Preview focus does that, and attach stays for full-screen work.

- **Keys** (`crates/ui/src/app/modes/preview_focus.rs`): in `preview-focus`, `App::on_key` hands every `KeyEvent` to `on_raw_key` before `terminal_input`/`handle_input`, so Ctrl+C never quits and the busy gate never swallows a key. Each event's raw `sequence` goes to `send_agent_input` as one `input` message, never coalesced, so the daemon's `answers_prompt` sees a lone Esc, Enter or digit and clears *needs you*. Mouse reports and kitty releases are skipped (the wheel comes through `on_stdin_text`). Outside a paste, `detach_position` (`crates/client/src/attach.rs`, which `is_detach_input` is built on) finds Ctrl+] / Ctrl+Space; what came before it is sent, then `leave_focus`. Unmodified arrows/Home/End take their `ESC O` form while the agent has DECCKM on (`application_cursor_key` in `crates/core/src/terminal_keys.rs`). Typing snaps the scroll offset to 0. Its keymap is the one binding Ctrl+].
- **Paste**: `sync_terminal_modes` turns bracketed paste on in `preview-focus` too; the markers toggle `in_paste` and are forwarded only when the agent has bracketed paste on (`screen.modes`), so a NUL inside a paste is pasted, not a detach.
- **Leaving** (`leave_focus`): Browse, `screen` cleared, and an unread reply marked read with `set-reply-read`, as `ui_loop::record_reply_read` does on detach. `interactive_focus_effect` (in `effect_pass`, before `sync_terminal_modes`) leaves by itself when the session stops running (*<title> exited; back to the session list*), when the selection moves to another session, or when the client goes.
- **Styled screen** (protocol v52): the preview watch carries `interactive` (`PaneWatchDeps.interactive`, the mode); the daemon keeps it per client (`ClientSubscription.preview_interactive`) and `sync_preview_styled` sends the worker `preview-mode {styled}` whenever "some client watches this session interactively" changes (watch, session switch, disconnect). A styled worker adds `screen` (`PreviewScreen`: per row, `ScreenSegment`s `[x, cells, text, fg, bg, flags]` from `line_segments`, the cursor only at offset 0 while DECTCEM shows it, and the modes) to its broadcasts and debounces them by 8 ms instead of 75 (`broadcast_delay`; not while attached), bringing a pending slow broadcast forward. The watch response asks the worker's snapshot for `styled`, so the first coloured frame needs no wait. The relay strips `screen` for plain watchers, so a second UI stays plain, and an unfocused message is byte-identical to v51's. `TerminalPreview::get_screen` has its own cache and dirty flag: sharing `dirty` with `get_snapshot` would make the activity heuristic see no change.
- **Drawing** (`render_preview_pane`, `render_screen`, `cell_style` in `crates/ui/src/panes/preview.rs`): only in focus and once `screen` arrived; until then (and after) the plain `content`, which is the same text, so entering and leaving never flash. Segments are placed at their emulator column and fitted to their `cells`, because the emulator measures widths (UnicodeV6) differently from ratatui. The 16 ANSI colours map to ratatui's named ones so the terminal's palette applies; dusk needs nothing (`apply_dusk` only resolves `Reset`, inverse and dim). `render_app` puts the terminal's real cursor on the agent's (`agent_cursor`, from the body rect the render stored), so IMEs compose there. The pane border is `border_active`, the badge `typing to the agent`, the footer `ctrl+] back • keys go to the agent • wheel ×N`. Frames are throttled to 16 ms in focus (`UiModel::render_throttle`).
- **Terminal focus** (`terminal-focus`, → on the Terminal tab while a shell is shown and live): the same raw key path (`on_raw_key`), sending `terminal-input {shell}` (`send_shell_input`) instead, with the shell's own paste and cursor-key modes; `preview_focus.shell` names it. The Terminal watch carries `interactive` and `shell` (`PaneWatchDeps.typing_shell`). It reads no reply on leaving. `interactive_focus_effect` leaves when the shell exits, another one or the action is shown, or the tab changes. The pane draws the shell's styled screen (`typed_screen`), the header says `typing into shell 2`, the cursor and border are as in preview focus, and the footer is `ctrl+] back • keys go to the shell`.
- **Not done** (`docs/future/preview-typing.md`): keyboard-protocol mirroring (Shift+Enter arrives as Enter in kitty-protocol terminals), click forwarding, holding frames during `?2026` synchronized updates.

### Preview scrolling

Claude, Pi and Codex all draw fullscreen in the alternate screen and scroll their own transcript on the mouse wheel. The worker launches Claude with `CLAUDE_CODE_NO_FLICKER=1` (over any inherited value; `agent_env` in `crates/worker/src/session.rs`) because Claude's classic renderer prints inline and ignores mouse input, which left nothing to scroll; Pi (fullscreen by default since 1.0) and Codex (`--no-alt-screen` is opt-out) need nothing.

Preview focus sends synthetic SGR mouse-wheel events to a running agent's PTY while its preview has no scrollback (the alternate screen keeps none). It used to scroll with `j`/`k`/`J`/`K`/`g`/`G` (`g`/`G` sending Ctrl+Home / Ctrl+End) and change the wheel speed with `+`/`-`; those keys now go to the agent, and the speed is set in Settings. An agent printing inline (Pi `tuiMode: "regular"`, Codex `--no-alt-screen`) leaves its history in Deckhand's worker-side scrollback, and Preview focus scrolls that instead. Attaching enters Deckhand's alternate screen and enables mouse reporting, so wheel events reach the agent as mouse events. Exited sessions show only the frozen `lastPreview` frame.

Both attach and Preview focus scale vertical wheel events by `scroll_speed` with `WheelScaler` (`crates/core/src/wheel.rs`): the running total restarts with each gesture (a direction change or 150 ms without events, `WHEEL_GESTURE_GAP`), so the first event of one always moves and nothing carries over; above 1 an event is repeated. The Settings row takes 0.5/1/2/3 or a custom value 0..=3 (`parse_scroll_speed`, two decimals), which also holds a value set with the old `+`/`-` keys. Attach picks up the latest value when entered. It replaced the TS's `attach_scroll_sensitivity` (default 0.12, a total that never reset): about 1 event in 8 reached the agent, the first notch of a scroll usually did nothing, and the remainder of one direction counted towards the other.

Claude's fullscreen renderer accelerates on fast scrolls by the gaps between wheel events (`wheelScrollAccelerationEnabled`, on by default), and its base speed is guessed from `TERM_PROGRAM`/`CURSOR_TRACE_ID`/XTVERSION, which inside Deckhand are the daemon's launch terminal's; the thinned, uneven stream read as random bursts. So, unless `claude_scroll_override` is false, Claude is launched with `--settings` carrying `env.CLAUDE_CODE_SCROLL_SPEED: "1"` and `wheelScrollAccelerationEnabled: false` (`integration_args`, passed whether or not hooks are on), plus `CLAUDE_CODE_SCROLL_SPEED=1` in its environment (`agent_env`; the daemon passes `scrollOverride` in the worker `start` message): with acceleration off Claude scrolls `max(1, floor(speed))` lines per event, so the events Deckhand forwards alone decide the distance. Why both: Claude applies each settings source's `env` over its process environment, low to high (user, project, local, flag = `--settings`, policy), and `/scroll-speed` saves to `~/.claude/settings.json` `env`, so the environment alone lost to anyone who had used it. `CLAUDE_CODE_NO_FLICKER` stays environment-only: Claude checks it before the `tui` setting, and its `/tui` writes `tui`, never `env`. Codex (0.163) and Pi (1.3, on macOS) scroll a fixed distance per event and need no launch changes.

### Attach mode

- The title is `dh/<pane> <session>`. Attach clears/resets inherited terminal modes before handing off, and cleanup resets scroll regions, mouse/focus tracking, bracketed paste, alternate-screen state, enhanced-keyboard modes and other child-owned modes.
- Detach keys: `Ctrl+Space` (primary) and `Ctrl+]`. Attach recognizes NUL `Ctrl+Space` plus the enhanced-keyboard encodings emitted when a child TUI enables CSI-u / modifyOtherKeys.
- Bracketed paste is mirrored across the PTY boundary: agent attaches enable it on the outer terminal, while Terminal/Git/Dev attaches enable it only when the workspace worker saw the child request `?2004h` (`terminalModes` in the attach response, passed through by `attachWorkspacePane`). This keeps a multi-line paste from arriving as separate Enter presses without forcing paste markers into arbitrary programs.
- A Terminal/Git/Dev attach ends only on detach or `<pane>-detached` (workspace retired); the agent exiting does not end it, and a shell or lazygit that exits does not detach automatically.
- Status line: every attach on a terminal of 5 rows or more shows a rule and Deckhand's status line in the bottom two rows: the session (its full title, a sub-session's `parent / child`, from `UiExitResult::Attach.statusTitle`; the terminal title keeps the sidebar's short one), its state (an agent) or the pane's name (`terminal`, `git`, `dev`, `action`), how many other sessions wait on you (`! N need you` and `◆ N unread replies`, counted apart as in the sidebar header), and the detach key. The count is the UI's (`StatusScope`: its checkout via `session_matches_scope`; read replies come with the sessions' `replyReadAt`), not the whole repository that the attach connection's `list` then `subscribe` covers (that subscription also delivers the attached session's exit, so it stays repository-wide); unlike the sidebar's `! N` it leaves out sessions that exited failed or interrupted. The program's PTY gets two rows less and its output is adjusted on the way so it never reaches them (`crates/client/src/attach_status.rs`, `HEIGHT`). Bottom, not top, because a scroll region that does not start at row 1 stops most terminals from saving a shell's lines to their scrollback (Terminal, Dev and actions are on the normal screen), and the full-screen attaches keep it in the same place for consistency (tried on top first). A screen switch inside the pane (vim or less in the Terminal) restores the scroll region, since some terminals reset it there. The note editor draws the same bar itself (*Notes*, terminal editor).

## Worktree behaviour

### Creation

New worktree creation is agent-agnostic: the daemon resolves/creates the target cwd, then launches the selected agent normally in it. It creates it with Deckhand's own `git worktree add` (`fallbackCreateWorktree` in `crates/sys/src/git.rs`) at the effective `worktree.location` template (default `~/.deckhand/worktrees/{name}`; `expandWorktreeTemplate`/`worktreeLocation` in `crates/sys/src/worktree_links.rs`), reusing an existing worktree/branch. The branch name comes from `worktree.branchName` (`{name}`/`{user}`, checked with `git check-ref-format --branch`) and starts per `worktree.branchFrom`: `current` (launch HEAD), `default` (local origin/HEAD target, else main, else master) or `origin` (bounded non-interactive `git fetch origin +refs/heads/<b>:refs/remotes/origin/<b>`, failure aborts creation; `--no-track`). The base it used is returned as `baseRef` and stored on the session (cleanup / create-pr `--base`); reused worktrees/branches keep the old launch-branch baseRef.

Repository creation scripts (`.claude/scripts/create-worktree.sh`, the TS's "worktree creation hook") are no longer run, reviewed or fingerprinted: the `worktree` settings cover what they did, and the hook added a second, confusing way to make worktrees. What stays for the worktrees and files they left behind: `WorktreeCreator::Script` still reads (nothing branches on `creator` after creation); `worktree.hook` in a deckhand.json or the global defaults is accepted and ignored (`SETTING_KEYS` in `crates/core/src/worktree_links.rs`; a global save through Settings drops it, since global saves rewrite the parsed settings); `project_fingerprint` keeps the TS's empty `creation-hook` part, so trust given before still holds; and the Git tab compares such worktrees (they record no `baseRef`) with the default branch (`CommittedBase::DefaultBranch`).

After a worktree is newly **created** (by either path, never for reused/attached ones), `applyWorktreeLinks` (`crates/sys/src/worktree_links.rs`) links the effective `worktree.symlink` / `worktree.files` entries. It never throws: missing sources, existing real content (kept), and parents that resolve outside the worktree (checked segment by segment before any mkdir, then by realpath) become notes stored as `worktree.links` on the session (shown in `i`, logged by the daemon). Existing symlinks are replaced atomically (temp link + rename). Effective settings merge in `resolveSettings` via `mergeWorktreeSettings`.

The worktree name (`sanitize_worktree_name`, `crates/sys/src/git.rs`) lowercases, allows `a-z0-9_-/`, replaces other characters with `_`, collapses repeated `_` and `/`, trims leading/trailing `/`, `_`, `-`, limits to 96 chars and falls back to `worktree`: `Fix API/Login Bug!` → `fix_api/login_bug`.

### Deletion safety

Worktree deletion is guarded in two layers (`cleanupBlockers`/`inspectSessionCleanup` in the daemon, `inspectWorkspaceCleanup` in `crates/sys/src/workspace_git.rs`), re-checked at kill/exit time, not just when the confirmation opens:

- structural blockers, never overridable: main worktree, the session's launch worktree, a worktree used by another non-exited session, no/unregistered worktree, and for branch deletion a protected (`main`, `master`) or changed branch
- data reasons, overridable only by typing `DELETE` (`allowDataLoss`): modified/untracked/valuable ignored files (ignored `node_modules` and any untracked/ignored entry that is itself a symlink, checked with lstat and capped at 2000 checks, are disposable), and, when deleting the branch or on a detached HEAD, commits not reachable from another branch or remote ref
- squash merges: Git never considers a squash-merged branch merged, so the "not reachable" count would demand `DELETE` for commits that were integrated. When the worktree has a merge marker with `mergeSourceSha` (Deckhand's merge/squash, a kept conflicted merge, or a PR found merged with its head commit present locally), `inspectWorkspaceCleanup(…, {integrated})` excludes that commit too (`rev-list HEAD --not --branches --remotes <sha>`, only after `rev-parse --verify` confirms it). Commits added after it still count; an unmarked worktree, a manual `M` (no SHA) or an unknown/invalid SHA change nothing.
- what would be lost is shown in full (`crates/ui/src/panes/cleanup.rs`, `cleanup_loss_lines`): the inspection returns the files themselves (`files`: changed, untracked, valuable ignored, at most `CLEANUP_FILES_LISTED` (100); the counts stay complete), and the kill confirmation, W's confirmation and both typed-DELETE screens list each reason on its own line and then every listed file (`M`/`?`/`!`, paths cut from the front), with `+N more` only for files beyond those the inspection names.

When safe, the kill confirmation offers: kill only / keep worktree (restartable), kill and delete worktree, kill and delete worktree and branch, cancel.

After Git unregisters a deleted worktree, Deckhand force-removes the worktree path to clear ignored/untracked remnants (only after `git worktree remove` succeeded, so only for a path Git had registered; symlinks are not followed, so link targets survive; tested). It prunes empty parents under `~/.deckhand/worktrees`, and for custom locations only the intermediate directories of a slash-containing worktree name (`rmdir`, empty only).

A deleted worktree is recorded on its worktree record (`deletedAt`), so every session of it, not only the killed one, is shown without restart/merge hints, refuses restart/merge/`M` (unmarking still works), and has no workspace (Terminal/Git/Dev say *its worktree was deleted*).

### Merge behaviour

Git in `crates/sys/src/git.rs` (`mergeWorktreeIntoCurrent`, `operationInProgress`, `commitWorktreeChanges`, `unmergedFiles`, `abortMerge`, `branchCreationCommit`, `branchHasOwnCommits`) and `crates/sys/src/workspace_git.rs` (`getMergePreview`, `mergedIntoDefault`, the injectable PR lookup); the daemon's `mergePreview`/`mergeSessionWorktree`/`resolveMerge`/`markSessionMerged`/`detectMerges` (`crates/daemon/src/merge.rs`); the screen model in `crates/core/src/merge_model.rs` (pure, unit-tested), rendered by `merge_pane_rows`/`conflict_pane_rows` in `crates/ui/src/app/modes/confirm.rs`.

- normal merge: `git merge --no-commit --no-ff <source>`; squash merge: `git merge --squash <source>`
- target is the Deckhand launch/current worktree, which must be on a branch; source is the selected session worktree's current branch, or its HEAD SHA if detached; source and target roots must differ
- **target checks** (`operationInProgress`, per worktree via `rev-parse --git-path`): a merge (MERGE_HEAD), rebase (`rebase-merge`/`rebase-apply`), cherry-pick, revert, or unresolved conflicts without MERGE_HEAD (a kept squash) refuse the merge with a message naming it (`operationProblem`); the preview shows the same line
- **preview** (`merge-preview`, read-only, a handful of bounded Git calls): `targetRoot`/`targetBranch`, `targetIsMain` (vs `resolveRepoContext().mainRoot`), `defaultBranch` (`resolveDefaultBranch`, local), `HEAD..<source sha>` count plus the first `MERGE_PREVIEW_COMMITS` (100; the TS had 6) commits as `MergeCommit` (short hash, commit time, subject; a bare subject string, as the TS sent, still deserializes), the numstat of `HEAD...<source sha>` (files, +/−), the source's uncommitted files (porcelain v2: changed + untracked, not ignored), and `overlap`: target paths with uncommitted changes that the committed diff touches (`committed`) or that the source's uncommitted files touch (`uncommitted`, which only counts while the toggle is on); capped at 200 each
- **confirmation screen** (`mergeConfirmLayout`): title; `Into <branch> · <compact target path>` (THEME.warn when `surprisingTarget`: not the main checkout, detached, or not the default branch when that is known); an in-progress warning; `N commits · F files +A −D` (`· +N uncommitted files` while the toggle is on; `No new commits` otherwise); the commits as `<hash> <age>  <subject>` (age from `MergeConfirmInput.now`, right-aligned so subjects line up; `+N more` beyond the 100 previewed); `N uncommitted files` and the toggle line `☑ commit them first ("<title>")` / `☐ … · they stay in the worktree`; the overlap warning; the started task and the open-items toggle; the three options naming the target branch; one hint line; a failed attempt's output; the notes. The model can budget a height (dropping notes, then error output, then subjects), but the UI lays it out with `MERGE_LAYOUT_ROWS` (100 000) so nothing is cut and the body scrolls instead (`MergeConfirmLayout.commit_rows` marks the scrolling part). Enter waits for the preview (or its error).
- **commit-first** (`merge-worktree` `commitFirst`, default on in the UI when the preview has uncommitted files): `git add -A` then `git commit --no-edit -m <session title>` in the source worktree, hooks running as usual (GIT_EDITOR=true); a failure throws *Commit failed in the worktree, so nothing was merged:* with the last 12 lines of output (whatever `add` staged stays staged). With it off, uncommitted files stay behind and a worktree with no commits is skipped (*No new commits to merge*); with it on, such a worktree merges its new commit
- before merging, Deckhand resolves the source commit (`mergeSourceSha`) and checks `HEAD..<sha>`; no new commits → `skipped`. Success records `mergedAt`, `mergeMode`, `mergeTargetBranch`, `mergeSourceRef`, `mergeSourceSha` on the worktree record, so every session of that worktree shows `✓`
- **conflicts**: Git exits nonzero with unmerged files → `conflicted: true`, `conflicts` (≤ 200 paths) and `conflictCount`; the daemon remembers the attempt per target root (`pendingMerges`: mode, source ref/SHA, target HEAD and whether the index was clean). The conflicts screen (`conflictView`) lists every file the result names (`+N more` only beyond those) and two keys: `enter` → `resolve-merge` `keep` (left in progress for the editor or the Git tab's conflicts group; the marker is set now, with the remembered SHA) and `x` → `abort`. Abort: with MERGE_HEAD, `git merge --abort`; a squash has none, so `git reset --merge` (what `merge --abort` runs), then SQUASH_MSG is removed, only for a squash this daemon started on a clean index whose target HEAD has not moved, otherwise it refuses (*Cannot abort this squash merge safely…*). Verified in fixtures: `reset --merge` restores the merged files and the index and keeps unrelated unstaged edits and untracked files; ort refuses any merge while unrelated changes are staged, so a conflicted squash always started on a clean index
- **merge detection** (`detectMerges`/`runMergeDetection`/`detectMergeFromSummary`/`markDetectedMerge`): live, unmarked records whose worktree Git still lists and whose directory exists, at most `MERGE_DETECT_MAX` (50) per run, one run at a time, grouped by repository (`git worktree list` + default branch once each). Ancestry (`mergedIntoDefault`, one `rev-list` per record whose tip moved past `baseSha`): the tip is reachable from `refs/heads/<default>` or `refs/remotes/origin/<default>` (never fetched) **and** has a commit of its own beyond `baseSha` (`merge-base --is-ancestor`, tip ≠ start) **and** the branch reflog shows a commit made on it (`commit…`, `cherry-pick…`, a non-fast-forward merge/pull; unknown when the reflog is empty → not required). So a fresh branch, one only fast-forwarded/reset to a newer main, the default branch itself and records without a starting point are never marked. PR: when a `workspace-summary` with `includePr` reports `MERGED` (catches GitHub squash merges), the record is marked `pr` with `mergeTargetBranch` = the PR base and `mergeSourceSha` = its `headRefOid` when that commit exists locally. Runs at daemon start, every `MERGE_DETECT_INTERVAL` (5 min) and after every `workspace-summary` (`i`) for that session's record. It never unmarks; `M` can clear a detected marker, after which `mergeDismissedTip` keeps detection away until the tip moves
- `M` (`mark-session-merged`) toggles the worktree's marker after external/manual resolution; it records no `mergeSourceSha` (deletion safety is not relaxed by an unverified claim)

## Agent identity, forks, and restarts

Claude and Pi get an exact native conversation ID (a UUID Deckhand generates) at launch, stored as an `id` ref, so resume never depends on name lookup or Pi's private file layout. The display label is `dh-{sanitized-title}-{short-id}`. Sessions persisted before this keep their `name` (Claude) or `path` (Pi) refs and resume as before. Codex launches without an ID; its native ID is captured from an authenticated SessionStart hook or the `codex resume <id>` exit hint (`codexResumeFromOutput`), and an unknown ID refuses resume (use `S`) rather than guessing `--last`.

Child session titles inherit parent context daemon-side as `parent title / child title` (trimmed to 64 chars); the sidebar strips that prefix for nested rows because it already shows the hierarchy.

### Per-agent table (`crates/core/src/agents.rs`)

`AGENTS` holds, per agent: `idAtLaunch` (Deckhand picks the conversation ID: Claude/Pi), `forks`, `forksAcrossDirectories`, `args(plan)`, the exit-screen readers (`exitRef`, `missingConversation`, `forkFailed`) and `version` (npm package of the latest release, the update command's args). A `LaunchPlan` is `new` (create, clean child, `S`), `resume` or `fork`; `launchArgs(program, plan)` turns it into argv. `relaunchPlan` decides what `s`/`S` launch (`forksParentAgain`: a forked child without its own conversation forks its parent again); the daemon only adds integration args (`agentSignals.integrationArgs`, appended after the plan's argv for every plan, so `codex fork <id> --no-daemon` like `codex resume <id> --no-daemon`) and handoff prompts. `readAgentExit` (daemon) applies the exit readers: the ref to keep, `failed`, and the note appended to the preview.

| --- | --- | --- | --- | --- |
| Claude | `--session-id <uuid> --name <label>` | `--resume <uuid>` (legacy name refs `--resume <name>`) | `--resume <parent uuid or legacy name> --fork-session --session-id <child uuid> --name <label>` | `--session-id <new uuid> --name <label>-fresh-<ts>` |
| Pi | `--session-id <uuid> --name <label>` | `--session-id <uuid>` (legacy `--session <path>`) | `--fork <parent id or legacy path> --session-id <child uuid> --name <label>` | `--session-id <new uuid> --name <label>-fresh-<ts>` |
| Codex | (no args) | `resume <id>` | `fork <parent id>` | (no args) |

Per-agent notes:

- Claude never gets `--session-id` without `--fork-session` on resume: it rejects that, and refuses an ID already in use. An unknown ID prints `No conversation found with session ID: <uuid>`; Deckhand marks the exit failed, appends a "press S" hint and refuses `s` for that ID, never starting fresh silently. On exit, Claude's printed `claude --resume "..."` command is parsed from the final preview and persisted (`id` kind for UUIDs, `name` otherwise); restart re-parses `lastPreview` too.
- Pi opens the exact project session ID with `--session-id`, or creates it if absent; `--fork` copies the parent before its TUI starts.

**Claude changes conversation ID without exiting**: accepting a plan with "clear context" (the reported bug: `s` reopened the plan, not the implementation that followed), `/clear`, `/resume`, `/branch`. The ref follows what is on screen, in two layers:

- Hooks (`acceptedNativeRef`): for `idAtLaunch` agents, any root event whose `session_id` differs replaces the ref (logged as *moved to conversation*). Not only SessionStart, because plan acceptance has sent none (anthropics/claude-code#20900, #20397; SessionStart's `clear` source covers `/clear`). Native subagent events never carry a ref; a fork never adopts its parent's ID; stale async hooks are dropped by `lastHookAt` first.
- Transcripts at `s` (`continuedConversation` → `latestClaudeConversation` in `crates/sys/src/claude_transcripts.rs`), for switches the hooks missed (hooks off, daemon down, a hook lost). It finds `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/*/<id>.jsonl` (the cwd's key first, then every project). Its family is that conversation plus the conversations in the same project that started after it and either share its first `custom-title` (Deckhand's `--name`, which plan acceptance keeps) or begin with a `parentUuid` from a member (plan acceptance does; it works through chains and renames). It resumes the member with the latest user/assistant message (latest message, not latest start, so a resumed and continued earlier conversation stays). Conversations other sessions own (forks) are excluded. Errors never fail a restart. Observed on 2.1.296 data; `/clear`'s title carry-over is not verified (the hooks cover it).

### Forks

- A fork copies the parent's conversation as saved at that moment (all three agents read the saved transcript); a turn still in progress in the parent is not included. Nothing is typed into the PTY.
- Create (`createSession`): the parent's agent must have `forks`; the child uses the parent's program; the parent needs an agent ref (Codex: *has not reported the parent's conversation ID yet*); an agent without `forksAcrossDirectories` refuses any worktree mode but `none` and any cwd other than the parent's (*Codex forks stay in the parent's worktree*), so it never fails at launch. `forkedFromAgentSessionRef` is the parent's ref at that moment. The child's `id` ref is stored at launch for Claude/Pi; Codex children start without one.
- Identity: `acceptedNativeRef` never replaces an `id` ref Deckhand assigned (forks included) and never lets a forked child adopt its parent's ID (stored `forkedFromAgentSessionRef` or the parent session's current ref) from a hook; `readAgentExit` ignores an exit hint naming the parent.
- `s` on a forked child (`relaunchPlan`): resumes its own ref; forks the parent again with a new child ID when it never launched, has no ref (Codex never reported one: the exit note says so), or holds the parent's ref (fork failed, or a legacy child). Fork failure: Pi prints `No session found matching` (parent has no saved session); Claude prints `No conversation found with session ID: <id>` for the parent, or for the child's own new ID (nothing was saved for it); either way `readAgentExit` stores the parent's ref, marks the exit failed and notes *Press s to fork the parent again, or S…*. A missing conversation on a non-fork still refuses `s` (*Use S*).
- `S` on a forked child starts a fresh conversation and drops `forkedFromAgentSessionRef`, so a later `s` never re-forks the parent over it.
- Legacy: Claude children stored with their `/branch` `name` ref resume by name; children still holding the parent's ref fork again with `--fork-session`; legacy `name`-ref parents fork with `--resume <name> --fork-session` (Claude's `--resume` accepts a name). Pi path refs keep `--session <path>` / `--fork <path>`.
- Forks into another worktree: every fork launch whose workspace differs from the parent's appends `-- <note>` (`movedForkPrompt` via `firstMessageArgs`, the same first-message mechanism as handoff children): it names the child's worktree and branch, says earlier paths under the parent's worktree belong to the parent and must not be read or edited, that the parent's uncommitted changes are not there, and asks the agent to confirm and wait. Forks in the parent's worktree send nothing.

Cross-directory forks (why Codex forks stay in the parent's worktree):

- Claude: verified by running Claude Code 2.1.287 against a throwaway conversation: `--resume <parent> --fork-session --session-id <child>` from another cwd stores the child under the child's cwd project, with the parent's history and nothing written to the parent.
- Pi (1.0.2, read from the installed package's `dist/main.js` and `dist/core/session-manager.js`, not run): `--fork <arg>` uses a path as is; an ID is looked up in the cwd's project, then across every project (`SessionManager.listAll`). `SessionManager.forkFrom(source, cwd)` copies the entries into a new file in the target cwd's project, and `--session-id` later finds it there. So Pi forks work from another worktree.
- Codex (0.157, from `codex fork --help` and strings in the installed binary; not run): sessions are rollout files under `$CODEX_HOME/sessions/%Y/%m/%d`, found by ID regardless of cwd. But resuming or forking a session recorded in another directory goes through the TUI's `cwd_prompt` (*Use session directory (…) / Use current directory (…)*, with *Always use …* stored as `tui.resume_cwd`), so a cross-directory fork could prompt or run in the parent's directory. That could not be established without a real run, so `forksAcrossDirectories` is false: the create form shows the fork staying in the parent's worktree (`tab` does nothing, a note says so) and the daemon refuses other modes. Its exit hint is the same `To continue this session, run: codex resume <id>`, naming the current thread.

### Agent versions and updates (`crates/core/src/agent_versions.rs`, `crates/sys/src/agent_version_check.rs`, `crates/ui/src/flows/agents.rs`)

| | `--version` prints | latest (npm `latest` dist-tag) | update command |
| --- | --- | --- | --- |
| Claude | `2.1.295 (Claude Code)` | `@anthropic-ai/claude-code` | `claude update` |
| Codex | `codex-cli 0.160.1` | `@openai/codex` | `codex update` |
| Pi | `1.0.4` | `@earendil-works/pi-coding-agent` | `pi update --self` (pi only; `--all` would also update packages) |

- Claude's native builds are published to npm with the same numbers. `latest` (not `stable`) is used because it is `claude update`'s default channel. `claude update` may refuse when auto-updates are disabled (`DISABLE_AUTOUPDATER`); that shows as a failed update with its output.
- **Pure** (unit-tested): `parseVersion` (first x.y.z, suffixes ignored), `compareVersions` (numeric), `agentUpdateStatus` (`up to date`/`update available`/`not installed`/`latest unknown`), `sessionOutdated` (running only; exited sessions use the installed version on their next start), `updateHint` (the header's `codex update · G` / `N agent updates · G`; the Agents screen moved from `U` to `G` when `U` became mark unread).
- **Daemon** (`AgentVersionChecker`, one per daemon): installed = `findOnPath(program)` on the daemon's PATH (the launches' env; `resolveProgramCommand` uses the same lookup and caches only hits) + `<binary> --version` (10 s), cached by realpath + mtime/size, only successful reads kept. Latest = `npm view <pkg> version` (10 s), cached; `refreshLatest(force)` shares one run; the daemon refreshes in the background at start and on a 30-minute tick that only looks up once the last check is 6 h old; `agent-versions` with `refresh` forces it (the Agents screen on open and `r`). Failures leave `latest` unset with `error`, never a failed request. `DECKHAND_AGENT_LATEST` (JSON program → version) replaces npm entirely: tests set it so they never reach the network. `snapshot` adds per-agent `running`/`outdated` counts and `updating`. `publishAgentVersions` broadcasts `agent-versions-updated` only when the JSON changed.
- **Update** (`update-agent`): refuses an agent not on PATH (*run deckhand setup*); runs `<binary> <updateArgs>` with stdin ignored, the daemon's env, cwd = home, its own process group, 5 min timeout (SIGTERM, then SIGKILL), combined output tail-bounded to 8000 chars; one run per agent (concurrent requests share it); then drops the `--version` cache, re-reads the installed version and responds `{ok, exitCode, command, output, before, after, versions}`. Output is returned at the end, not streamed. Sessions are never touched.
- **Session version**: `startWorker` reads the launched binary's version beside the spawn and patches `agentVersion` before the callers save the running session (create, `s`, `S`).
- **UI** (`AgentsFlow`, mode `agents`, full width like Settings): rows label · installed · latest · outdated sessions, status right; a details box (running state or the result with the output's last 8 lines first, then installed/path, latest/package/checked, update command, sessions, error); enter confirms first when the agent has running sessions; esc leaves while an update keeps running (the footer reports the end).

## Persistence and protocol

The state directory's files are listed in [docs/architecture.md](docs/architecture.md#state-and-logs). Beyond that:

- `DECKHAND_HOME` replaces `~/.deckhand` for every path. `scripts/deckhand-dev.sh` uses it to run a dev-channel daemon (`DECKHAND_CHANNEL=dev`) in `~/.deckhand-dev` (or `DECKHAND_DEV_HOME`); only that channel accepts the `shutdown` request used by `scripts/deckhand-dev.sh stop`.
- Files are written atomically (temp + rename) with 0600 files in 0700 directories (notes, handoffs). `config.json` is written under a lockfile shared by UI and daemon, keeping unknown keys and key order.
- `config.json` (`AppConfig` in `crates/protocol/src/records.rs`): `defaults` (global deckhand.json-schema settings, validated where used by `globalDefaults`/`resolveSettings`), `trustedProjects` (trust root → up to 20 fingerprints, newest first), `agent_hooks` (unset: on for Claude only; true adds Codex; false off), `notifications` (default off), `scroll_speed` (default 1, 0..=3), `claude_scroll_override` (unset: on), `theme` (`"dusk"` or the terminal's colours), `sidebar_width_percent` (`<`/`>`), `dev_command` (legacy fallback after `defaults.devCommand`) and `attach_scroll_sensitivity` (v2's setting, kept as stored but unused).
- Workspaces are not persisted (derived by `workspaceKey`); worktree records are (`worktrees` in `state.json`).

Protocol: NDJSON; current version **v53** (`PROTOCOL_VERSION` in `crates/protocol/src/lib.rs`, also sent by every worker in its `Hello`). Bump it on any request/response shape change. History (v44–v53 are the port's own; see the history of `crates/protocol` for v44–v46):

## Codex hooks

`deckhand hooks codex` prints the hooks JSON for `~/.codex/hooks.json` (Codex lacks `Notification` and `StopFailure`; `deckhand hooks` without an argument prints the Claude-style settings minus `Interrupt`). Each entry runs `'<deckhand>' 'hook'`, where `<deckhand>` is the `deckhand` found on `$PATH` when it is this very executable, else the running executable. Deckhand never writes into the Codex home. Settings (`C`) and `deckhand doctor` (read-only, honours `CODEX_HOME`) warn when Codex's hooks are missing, belong to another install, or still call the old TS bridge (`node ... cli.js hook`); the fix is always to regenerate with `deckhand hooks codex` and review with `/hooks` in Codex.

## How to run locally

```bash
cargo build -p deckhand
scripts/deckhand-dev.sh --sandbox    # isolated state in ~/.deckhand-dev, disposable repository
scripts/deckhand-dev.sh stop         # stop only the dev daemon
```

Never run the plain debug binary against your real home, and never `cargo install` while testing a branch. To update your everyday Deckhand from the checkout, run `cargo install --path crates/deckhand --locked`, then `deckhand restart` if the daemon changed. Don't mix that with the release installer on the same machine (`~/.local/bin` shadows `~/.cargo/bin`). More in [docs/dev-build.md](docs/dev-build.md).
